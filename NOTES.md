# Notes

- User reads/writes Traditional Chinese comfortably; prior study material (hello_rust) was the Traditional Chinese translation of the Rust book. Default to Traditional Chinese for lesson prose; code and official terminology stay in English.
- User's local toolchain: rustc 1.94.0 / cargo 1.94.0 (already installed, verified 2026-08-04) — no setup lesson needed for installation.
- Treat as a true beginner per explicit request ("從頭全部重來") — do not assume retention of anything in hello_rust/branches/functions/variables even though the files exist on disk.
- **Prose style: short sentences, one idea each.** User flagged Lesson 9 as 饒口 (a mouthful). The offender was a single sentence chaining three separate ideas with `——` and 「」. Avoid: long clause chains, `——` used to bolt on a second thought, quoted "the compiler is saying…" dramatisations, and restating a standard term as a description. Prefer one claim per sentence, one idea per paragraph, and the standard term stated plainly. This is about sentence construction, not depth — the user wants precision (see learning record 0002), just delivered in shorter units.
- **Don't swap a mechanism the user already understands for a metaphor.** User flagged 「往 String 走要花錢，往 &str 走免費」as 怪怪的. The preceding line had already said 配置記憶體 + 複製內容 — the metaphor replaced something concrete with something vaguer. Metaphors earn their place only when the mechanism is *not yet* established (the notebook for borrowing worked because ownership was abstract). Once the mechanism is on the page, state it directly: 「向系統要一塊新記憶體，再整份複製進去，字串越長越慢」. Same trap as restating a standard term as a description.
- **Code blocks must be runnable as written.** The user typed `s.len()` from a Lesson 12 callout and got `unused_must_use`. I had written bare expressions with `// 12` comments meaning "this evaluates to 12", but the block reads as a program. Wrap value-producing expressions in `println!` — or if a block genuinely isn't runnable, say so above it. The user types code blocks in verbatim; treat every one as a promise.
- **Refer to compiler errors by their message text, not their code.** User's point: people read the English sentence, not `E0502`. Say "編譯器說 `cannot borrow ... as mutable because it is also borrowed as immutable`", and mention the code only where it's actually useful for lookup (`rustc --explain`, search, reference cards). Applies to lesson bylines, exercise steps, win boxes, and quizzes alike.
- **Quiz stem and options must ask the same question.** A Lesson 12 question asked 「`s.len()` 的值是多少？」 (a *what*) but every option was 「6，因為每個中文字元在 UTF-8 佔三個位元組」 (a *why*). The user read the reason as the thing being tested. Fix: keep the reason in the feedback, make options bare answers. Bonus from the rewrite — asking for `len()` *and* `chars().count()` together tests the actual distinction instead of one recalled number.
- **Never quiz on error-code numbers.** Related but separate: a Lesson 11 question asking the user to recall `E0502` tested memorisation with no downstream payoff — the compiler prints the code every time. Replaced with "here is the failing snippet, which fix is right?", which tests the non-obvious rule instead (a borrow ends at its last use, so reordering fixes it). General rule: quiz on what you'd have to *decide*, never on what the tool already tells you.
- **Check that Chinese renderings of English terms don't fight the concept.** User found 「借來改」（mutable borrow）「好奇幻」: Chinese 借 defaults to *taking away*, which is what `move` does, not what borrow does. A one-paragraph physical metaphor fixed it (a notebook left open on your desk — `&` is a colleague reading it, `&mut` is a colleague writing in it, `move` is someone taking the whole notebook). The metaphor then made the two borrow rules feel inevitable rather than arbitrary. Before shipping a lesson, check whether the translated term implies the wrong thing; if so, lead with a concrete physical scene, not with syntax.
- **Never use an undefined term.** Lesson 10 first draft was reported as 看不懂, and the cause was vocabulary, not sentence length: 作用域, trait, 記憶體釋放, double free were all used as if already known. Before writing a lesson, check every non-obvious term against `GLOSSARY.md`. If it isn't there, either define it inline with a runnable example first, or don't use it. Comprehension failures here look like style complaints but are usually a missing definition.
- **Don't quiz on a fact that only appeared inside a code comment or a dense multi-fact intro paragraph.** Lesson 14's quiz 3 asked which `Option` variant carries data (`Some`); the only place that fact appeared was a `//` comment next to a code example, and one clause buried in an intro paragraph that also introduced `Result`/`Ok`/`Err`/`None` in the same breath. User's point: that's not memorable, so the quiz tests "did you read the comment" not "do you understand." Fix: before quizzing a fact, check it has its own bolded, standalone sentence in the prose — not just a code comment or one clause inside a paragraph covering several other new terms.
- **User's TypeScript background is a strong teaching lever for abstract Rust concepts — lead with it, don't append it.** Explained `impl Trait for Type` (Lesson 16, `Display`) with plain prose first ("填契約", "遵守規格"); user said they couldn't follow it. Rewrote leading with a TS `interface`/`implements` code side-by-side, then the Rust reading — landed immediately. When a concept has no concrete mechanism yet on the page (traits, generics, anything "shape of a contract"-like), reach for the TS analogy first, not as a fallback after prose fails. This doesn't contradict the "don't swap a mechanism for a metaphor" rule (NOTES.md above) — that rule is about replacing an already-concrete mechanism; traits/generics start abstract, so an analogy is the concrete anchor, not a downgrade.
