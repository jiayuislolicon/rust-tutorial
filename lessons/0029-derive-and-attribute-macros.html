Lesson 0029 · Rust · CLI 工具養成路線

編譯器能產生的 impl，就別手寫：#[derive]

學習目標：你的測試避開了一種更短的寫法，原因不是偷懶。你會找出那個原因，用一行修好它，並把從 Lesson 20 起就一直在寫的 #[...] 正式命名。

1. 你自己的測試裡，藏著一個繞路寫法

打開 hello_cli/src/report.rs，看看 classify_line 的三個測試： 

#[test]
fn classify_line_empty() {
    assert!(matches!(Report::classify_line(""), LineKind::Empty));
}

前面學過更短的相等檢查：assert_eq!(a, b)。試著把這個測試改成那種寫法： 

assert_eq!(Report::classify_line(""), LineKind::Empty);

跑一次 cargo test——編譯器拒絕了：

error[E0369]: binary operation `==` cannot be applied to type `report::LineKind`
help: consider annotating `report::LineKind` with `#[derive(PartialEq)]`

error[E0277]: `report::LineKind` doesn't implement `Debug`
   = note: add `#[derive(Debug)]` to `report::LineKind` or manually `impl Debug for report::LineKind`

兩個錯誤看起來分開，其實各指出一個缺口：LineKind 既不能做 ==，也不能用 {:?} 印出來。你原本的 matches!(expr, Pattern) 走的是模式比對：它拿 Report::classify_line("") 的結果去對 LineKind::Empty 這個 pattern，對得上就回傳 true。整個過程沒有相等比較，也不需要把值印出來。

assert_eq!(a, b) 就不一樣了。它得先用 a == b 判斷相等；如果不相等，還得把兩邊用 {:?} 印出來，讓你看見差在哪。因此它同時要求兩個 trait：PartialEq（提供 ==）和 Debug（提供 {:?}）。這一課要學的，就是把這兩樣用最快的方式補上。

2. #[...] 到底是什麼

從 Lesson 20 起，你就一直在寫這種行——只是還沒替這套語法取名字：

#[test]
fn classify_line_empty() { ... }

#[cfg(test)]
mod tests { ... }

#[...] 叫做 attribute（屬性）。你可以把它想成一張便利貼，貼在正下方那一項上面；編譯器在編譯時讀它，不是程式跑起來才執行的程式碼。#[test] 告訴 cargo test 的執行器：「呼叫這個函式，看它會不會 panic」。#[cfg(test)] 告訴編譯器：「只有為測試編譯時，才把下面這項收進來」。這兩行都不會在執行時自己做事；它們改的是編譯器怎麼對待被貼著的那一項。

同一套語法還有第三種用法。#[derive(...)] 既不標記某一項，也不決定要不要編譯——它直接幫你寫程式碼。

3. #[derive(...)]：自動產生 Trait 的 impl

它寫出來的東西，形狀你其實見過。打開 hello_cli/src/errors.rs： 

impl fmt::Display for AppError {
    fn fmt(&self, f: &mut fmt::Formatter) -> fmt::Result {
        match self {
            AppError::Empty => write!(f, "empty file"),
            // ...
        }
    }
}

#[derive(PartialEq)] 的意思是：請編譯器在編譯時，自動替這個型別產生 PartialEq 的實作。

概念上，它就像我們自己寫了：

impl PartialEq for LineKind {
    // Rust 自動產生比較邏輯
}

PartialEq 的比較規則是：兩個值必須是同一個 variant，而且如果 variant 帶有資料，那些資料也必須相等。

例如：


LineKind::Empty == LineKind::Empty // true
LineKind::Empty == LineKind::Code // false

把它加在 LineKind 上面：

🔴 修改前 —— 沒宣告任何能力
pub enum LineKind {
    Empty,
    Comment,
    Code,
}
🟢 修改後 —— 能比較、也能印出
#[derive(Debug, PartialEq)]
pub enum LineKind {
    Empty,
    Comment,
    Code,
}

再跑 cargo test，這次能編譯也能通過。assert_eq!(Report::classify_line(""), LineKind::Empty) 的寫法，跟用在 i32 上完全一樣。

這裡有兩個 trait，各自對應 assert_eq! 的一個需求：

  • PartialEq：讓 == 可用，所以能判斷兩邊是不是相等。
  • Debug：讓 {:?} 可用，所以在檢查失敗時能把兩邊印出來。

兩個缺一不可；拿掉任何一個都會回到剛才的編譯錯誤。只加 #[derive(PartialEq)] 仍然編不過——error[E0277]: doesn't implement Debug——因為 assert_eq! 展開成真正的程式碼時，會把失敗時要印出的格式化邏輯也一併編進去。就算這次測試實際上會通過，編譯器仍然要求那段印出的程式碼必須能編譯。

所以這裡的 Debug 不是裝飾；沒有它，失敗的斷言根本讀不懂。你可以自己確認：format!("{:?}", LineKind::Comment) 印出 Comment——推導出來的 Debug 在這個例子裡，就是把 variant 的名字印出來。

4. 不是每種 trait 都能 derive

回到 impl fmt::Display for AppError。為什麼這一份要手寫，而 PartialEq 和 Debug 可以讓編譯器產生？

#[derive] 只能用在「從型別的結構就能唯一決定實作方式」的 trait 上——編譯器必須能照一套沒有歧義的規則，把整份 impl 機械地寫出來。比較兩個 LineKind，自然的規則就是「同一個 variant（以及裡面的資料相同）才算相等」；印出 LineKind 也有固定格式可循。所以 PartialEq、Debug 都能 derive。

但 AppError::Empty 要顯示成 "empty file" 還是 "nothing here"，那是你在寫使用者訊息時的選字判斷，不是結構本身能決定的事。一旦中間需要人做選擇，就得回到手寫 impl。

下面這些 trait 都符合「有固定規則可循」，所以可以 derive：

Trait derive 之後你得到什麼
Debug {:?} 印出 —— variant / 欄位名稱，加上它們的值
PartialEq == / !=，因此也能用 assert_eq!
Eq 疊在 PartialEq 上面的更嚴格承諾（每個值都等於自己，沒有例外）—— 當 HashMap 的 key 時需要
Clone 一個明確的 .clone() 方法，用來複製這個值
Copy 見 GLOSSARY.md 的 Copy trait —— 只有每個欄位也都是 Copy 才合法
Default 一個 Type::default() 建構子，每個欄位用它自己的預設值
Hash 讓這個值能當 HashMap 的 key

每一個都附帶一個條件：你的型別裡每個欄位也必須實作那個 trait，derive 才能編過。一個裝著 String 的 struct 可以 derive Clone（String 是 Clone），但不能 derive Copy（String 不是）。

💡 如果 #[derive(Something)] 失敗，錯誤是 error[E0277]: the trait bound `Field: Something` is not satisfied，那不是 derive 壞了——是這個型別自己的某個欄位還沒有那個能力。

5. 把另外兩個測試也修好

#[derive] 加上之後，把剩下兩個測試也改成同一種寫法：

🔴 修改前
assert!(matches!(Report::classify_line("// hi"), LineKind::Comment));

assert!(matches!(
    Report::classify_line("let x = 1;"),
    LineKind::Code
));
🟢 修改後
assert_eq!(Report::classify_line("// hi"), LineKind::Comment);

assert_eq!(Report::classify_line("let x = 1;"), LineKind::Code);

classify_line 本身完全沒改。你在 enum LineKind 上面加的 #[derive(Debug, PartialEq)] 就是全部的修復。跑一次 cargo test，確認全部通過。

6. 三種 attribute，三件不同的工作

Attribute 它實際在做什麼
#[test] 標記一個函式，讓測試執行器去呼叫它
#[cfg(test)] 只有在為 cargo test 編譯時，才把下面這項收進來
#[derive(Trait, ...)] 照固定規則，寫出一份或多份 impl Trait for Type

Attribute 是這三種寫法的總稱。#[derive] 是其中會真正產生程式碼的那一種，所以值得一眼就認出來：任何 struct 或 enum 上面寫了 #[derive(...)]，它就已經有那些 trait 實作——即使檔案裡完全看不到對應的 impl。
