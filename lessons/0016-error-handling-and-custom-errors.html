錯誤處理與自訂錯誤型別

目標：用一個自己定義的 enum 統一表達 hello_cli 所有可能的失敗原因，並讓它能用 {} 印出乾淨的錯誤訊息。

現在 hello_cli 只有一種會失敗的情況：fs::read_to_string 讀不到檔案，回傳 Err(error)，error 是 io::Error。但真實的 CLI 工具通常不只一種失敗方式——比如檔案讀到了，但內容是空的，這也該算失敗，只是原因不同。現在這兩種失敗沒有共同的型別可以裝，只能各自處理。

用 enum 把失敗原因收在一起

Lesson 14 教過 enum 可以帶資料。錯誤處理正好用得上這個能力——定義一個自己的 enum，一個變體對應一種失敗原因： 

enum AppError {
    ReadFailed(std::io::Error),  // 讀檔失敗，把原始錯誤包起來
    Empty,                       // 檔案是空的
}

這就是自訂錯誤型別：把「這個函式可能會怎麼失敗」列成一個 enum，當作 Result<T, E> 裡的 E。呼叫端只要 match 這一個型別，就能處理所有失敗原因，不用再各自猜測。

讓它能印出來：Display trait

現在寫 println!("{}", err) 會直接編譯失敗。原因：AppError 還沒有人告訴它 {} 該印什麼字。

先看 TypeScript 版本，概念完全對應： 

// TypeScript
interface Display {
  fmt(): string;
}
class AppError implements Display {
  fmt() { return "..."; }   // 這裡自己決定要印什麼
}

interface Display 只規定「要有一個 fmt，回傳字串」，不管內容。class AppError implements Display 才是真正把 fmt 寫出來，決定印什麼字。

Rust 的 trait 就是 TypeScript 的 interface；impl Trait for Type 就是 implements。同一件事，換一種語法： 

use std::fmt;

impl fmt::Display for AppError {
    fn fmt(&self, f: &mut fmt::Formatter) -> fmt::Result {
        match self {
            AppError::ReadFailed(e) => write!(f, "讀不到檔案：{}", e),
            AppError::Empty => write!(f, "檔案是空的"),
        }
    }
}

對照剛才的 TypeScript：impl fmt::Display for AppError 對應 class AppError implements Display。fn fmt(&self, f: ...) -> fmt::Result 這個函式的名字、參數、回傳型別，是 Display 規定好的，不能改——對應 TS 那邊 fmt(): string 的簽名。函式裡面的 match self { ... }，才是你自己決定要印什麼，對應 TS 那邊 { return "..."; }。

write!(f, ...) 跟 println!(...) 語法幾乎一樣，差別是它把結果寫進 f，不是直接印到畫面上。記住「match self，每個變體 write! 一句話」就夠用。

一個小提醒：impl Report（沒有 for）是幫 Report 加方法，跟 trait 無關。impl Display for AppError（有 for）才是「實作一個 trait」。看到 for 就知道這是在填別人規定好的介面，不是在加自己的新方法。

填完 fmt 之後，println!("{}", err)、err.to_string() 都會自動去呼叫你寫的這個 fmt。

你其實一直在受益於別人寫好的 Display 實作：io::Error 早就實作了 Display，這就是為什麼 println!("讀不到檔案 {}：{}", filename, error) 這行程式碼一直能正常印出訊息。

小測驗一：為什麼 hello_cli 要自己定義 AppError，而不是繼續讓每個函式各自回傳 io::Error 或字串？
小測驗二：println!("{}", err) 要能正常印出 err，err 的型別必須符合什麼條件？

換你動手

四個步驟：
  • 在 main.rs 最上面定義 enum AppError { ReadFailed(std::io::Error), Empty }。
  • 幫 AppError 實作 impl std::fmt::Display for AppError，兩個變體各自 write! 一句中文錯誤訊息。
  • 寫一個新函式 fn load_report(filename: &str) -> Result<Report, AppError>：用 match fs::read_to_string(filename) 判斷——Err(e) 就回傳 Err(AppError::ReadFailed(e))；Ok(content) 但 content.trim().is_empty() 就回傳 Err(AppError::Empty)；否則回傳 Ok(Report::new(filename, content))。
  • 把 main 裡原本的 match fs::read_to_string(filename) { ... } 換成 match load_report(filename) { Ok(mut report) => { ... }, Err(err) => println!("{}", err) }，其他邏輯（add_title、summary、count_kinds）搬進 Ok 分支裡。

成功條件：cargo run -- notes.txt 對存在且有內容的檔案照常運作；對不存在的檔案印出「讀不到檔案：...」；對一個內容全空白的檔案（可以用 cargo run -- empty.txt 搭配一個空檔案測試）印出「檔案是空的」。

這一課的成果
hello_cli 現在有一個真正的錯誤型別，把「讀不到檔案」「檔案是空的」這兩種不同失敗原因收在同一個 Result 裡，呼叫端一次 match 就能處理完，訊息還印得乾淨。這直接對應 MISSION.md「處理錯誤而不 panic」這條成功標準——而且是用 struct、enum、trait 三個東西一起搭出來的，不是孤立的語法練習。速查表：錯誤處理與自訂錯誤型別參考卡。
