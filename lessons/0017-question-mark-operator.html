? 運算子與 From trait

學習目標：把 load_report 裡冗長的錯誤轉發 match 換成 ? 運算子，並理解 ? 如何透過 From trait 自動將 io::Error 轉為 AppError。

重構前 vs 重構後

我們先來看看這堂課最終要達成的效果。手寫 match 轉發錯誤十分冗長，而使用 ? 能大幅簡化程式碼。

🔴 重構前：手寫 match 轉發錯誤

拿到 e 之後包一層 AppError::ReadFailed 原封不動丟出去，沒有任何計算，純粹是樣板程式碼： 

fn load_report(filename: &str) -> Result<Report, AppError> {
    match fs::read_to_string(filename) {
        Err(e) => Err(AppError::ReadFailed(e)),
        Ok(content) => {
            if content.trim().is_empty() {
                Err(AppError::Empty)
            } else {
                Ok(Report::new(filename, content))
            }
        },
    }
}

🟢 重構後：使用 ? 運算子簡化

一行程式碼同時完成「檢查失敗並提早 return」與「錯誤型別自動轉換」： 

fn load_report(filename: &str) -> Result<Report, AppError> {
    // ? 一行搞定提早回傳與型別轉換！
    let content = fs::read_to_string(filename)?;

    if content.trim().is_empty() {
        Err(AppError::Empty)
    } else {
        Ok(Report::new(filename, content))
    }
}

1. ? 運算子的行為機制

? 只能接在回傳 Result 的運算式後面（例如 fs::read_to_string(filename)?）。它的運作邏輯如下：

  • 如果是 Ok(v)：拆包拿出裡面的值 v，交給後面的程式碼繼續執行。
  • 如果是 Err(e)：讓整支函式立刻提早結束（return），將錯誤傳出。後面的程式碼完全不會執行。
💡 快速理解：把 ? 想成「提早離場的檢查哨」——東西沒問題就放行通過；東西有問題，整個人直接被請出函式。

執行範例模擬

  • 檔案存在（如 "notes.txt"）：read_to_string 回傳 Ok("內容") → ? 抽出字串給 content → 繼續執行 if 判斷。
  • 檔案不存在（如 "missing.txt"）：read_to_string 回傳 Err(io_error) → ? 讓 load_report 立刻結束並回傳 Err → 後續的 if 完全不執行。

2. 關鍵問題：型別不匹配

若直接套用 ?，編譯會失敗！原因在於兩邊的錯誤型別不一致：

  1. fs::read_to_string 回傳的錯誤是：std::io::Error（標準函式庫定義）
  2. load_report 宣告回傳的錯誤是：AppError（我們自訂的）

當 ? 準備將 io::Error 回傳時，發現與函式宣告的 AppError 型別不合，編譯器就會報錯：? couldn't convert the error to AppError。

3. 解法：用 From trait 教 ? 如何轉型

標準函式庫中的 From trait 專門用來處理型別轉換。你可以把它想像成一個型別轉接頭（例如「歐規插頭 → 台規插座」）。

只要我們幫 AppError 實作 From<std::io::Error>，就能教 Rust 如何自動轉換型別： 

impl From<std::io::Error> for AppError {
    fn from(e: std::io::Error) -> AppError {
        AppError::ReadFailed(e)
    }
}

這段程式碼做了什麼？

  • impl From<std::io::Error> for AppError：宣告 AppError 具備將 io::Error 轉為自身的能力。
  • fn from(e: std::io::Error) -> AppError：當 ? 遇到 io::Error 時，幕後會自動呼叫 AppError::from(e)，包裝成 AppError::ReadFailed(e) 再回傳！

4. 錯誤來源的兩大分類

重構後的 load_report 包含兩種不同來源的錯誤處理方式：

fn load_report(filename: &str) -> Result<Report, AppError> {
    let content = fs::read_to_string(filename)?;   // 1. 轉發錯誤：來自外部函式，用 ? + From
    
    if content.trim().is_empty() {
        Err(AppError::Empty)                        // 2. 自訂錯誤：自己判斷的，直接寫 Err(...)
    } else {
        Ok(Report::new(filename, content))
    }
}
錯誤類型 觸發情境 處理方式
轉發錯誤 呼叫其他會回傳 Result 的函式失敗（如讀檔） 使用 ? 運算子（搭配 impl From）
自訂錯誤 自己邏輯判斷出的異常（如檔案內容為空） 直接手寫 Err(AppError::...)
小測驗一：fs::read_to_string(filename)? 這一行，如果檔案讀不到，接下來會發生什麼事？
小測驗二：load_report 回傳 Result<Report, AppError>，裡面用 fs::read_to_string(...)?（回傳 Result<String, io::Error>）。要讓這行 ? 編譯過，還需要什麼？

換你動手

實作兩步驟：
  1. 在 AppError 的定義下面，加上 From 的實作： 
    impl From<std::io::Error> for AppError {
    fn from(e: std::io::Error) -> AppError {
        AppError::ReadFailed(e)
    }
}
  2. 把 load_report 改寫成使用 ?： 
    let content = fs::read_to_string(filename)?;
    刪除外層手動的 match，保留底部的 if content.trim().is_empty() ... 邏輯。

驗證條件：執行 cargo build 無錯誤，且 cargo run -- notes.txt 對於正常檔案、不存在檔案、空檔案的行為與 Lesson 16 完全一致。

這一課的成果
load_report 現在用 ? 取代手動 match 轉發錯誤，配合 impl From<io::Error> for AppError 讓型別自動轉換。這是 Rust 錯誤處理最常見的寫法——之後每次呼叫回傳 Result 的函式，都可以用同一招。速查表：? 運算子與 From trait 參考卡。
