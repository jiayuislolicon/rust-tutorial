Lesson 0027 · Rust · CLI 工具養成路線

悄悄過期的欄位：當快取不再可靠

學習目標：你的工具印出了兩個互相矛盾的數字，但編譯器卻一聲不吭。你會找出原因，寫一個測試來鎖定你真正的意圖，然後用兩種不同的方式修復它。這裡真正的核心技能是：學會閱讀 struct，並一眼看出哪個欄位是需要手動保持同步的「地雷」。

1. 你的工具在對你說謊

用你的工具跑一次 notes.txt：

cargo run -- --count-only notes.txt
notes.txt：共 3 行
空行 0 行，註解 0 行，程式碼 4 行

總共 3 行，但程式碼卻有 4 行？這兩個數字都來自同一個檔案、同一次執行，但它們卻互相打架。沒有任何東西崩潰，結束代碼（exit code）也是完美的 0。

這比你在 Lesson 26 遇到的錯誤更糟。那些錯誤會讓程式停下來並印出警告。但這個 Bug 卻是塞給你一個錯誤答案，而且還表現得自信滿滿。

來看看 report.rs 裡這兩個數字是從哪來的：

pub fn new(filename: &str, content: String) -> Report {
    let line_count = content.lines().count();   // 只在這裡算過一次

    Report { filename: filename.to_string(), content, line_count }
}

pub fn summary(&self) -> String {
    format!("{}：共 {} 行", self.filename, self.line_count)   // 讀取存好的數字
}

pub fn count_kinds(&self) -> (usize, usize, usize) {
    // 每次呼叫時，都會重新計算 self.content.lines()
}

而這是在 main.rs 裡，卡在它們之間執行的那個方法：

report.add_title();          // <- 就是它
println!("{}", report.summary());
let (empty, comment, code) = report.count_kinds();
pub fn add_title(&mut self) {
    let title = format!("=== {} ===\n", self.filename);
    self.content.insert_str(0, &title);
}

add_title 往 self.content 裡多塞了一行。 count_kinds 重新計算，所以看到了 4 行。但 line_count 是在標題出現前就算好的，所以它還是 3。它再也沒有機會更新了。

💡 這個模式是有名字的。當一個欄位的值是從另一個欄位推導（derived）出來的，它就是一個快取（cache）。當來源改變，快取卻沒有跟著更新時，我們就說這個快取過期（stale）了。這是軟體工程中最古老的 Bug 形狀之一，而且 Rust 並不會保護你免受其害。

2. 為什麼編譯器一聲不吭

在過去的六課裡，Rust 總是不留情面地拒絕編譯你的錯誤。所有權、借用、窮盡的 match、錯誤轉換。那為什麼這次它卻放過你了？

因為編譯器根本不知道 line_count 和 content 有任何關係。用編譯器的視角來看看這個 struct： 

pub struct Report {
    pub filename: String,
    pub content: String,
    pub line_count: usize,   // 只是一個 usize。沒有任何東西把它和 content 連在一起。
}

對你來說，line_count 的意思是「content 裡的行數」。但對編譯器來說，它就只是一個剛好坐在 String 旁邊的 usize。這層關係只存在你的腦海裡，以及 new 函式裡那行剛好把它算出來的程式碼中。

而且 &mut self 給了方法修改任何欄位的權限。add_title 當然可以只動 content 而不碰 line_count，因為這正是 &mut self 賦予它的權力。

這就是 Rust 幫你檢查的真實邊界：

編譯器抓得到的 編譯器抓不到的
在值被 move 之後繼續使用 存起來的數字現在已經過期了
同時存在兩個可變借用 兩個應該要同步的欄位卻互相矛盾
你忘記寫的 match 分支 你忘記更新的欄位

左邊那一欄關乎記憶體安全。右邊那一欄關乎意義，而賦予意義是你的工作。Rust 非常擅長前者，但對後者完全沒有意見。

3. 用測試把「意義」釘死

既然這層關係只存在你的腦海裡，那就把它寫在會報錯的地方。把這段加到 report.rs 最底下的 tests 模組裡： 

#[test]
fn summary_agrees_with_count_kinds() {
    let mut report = Report::new("t.txt", "a\nb\nc\n".to_string());
    report.add_title();

    let (empty, comment, code) = report.count_kinds();
    assert_eq!(report.line_count, empty + comment + code);
}

跑一次 cargo test：

assertion `left == right` failed
  left: 3
 right: 4

這就是你在終端機裡看到的那個 Bug，現在它被困在自動化測試裡了。注意這個測試斷言（assert）了什麼：它不是說「line_count 必須是 3」，而是說「這兩種計算行數的方式必須一致」。如果測試只是死盯著數字 3，那就算工具的邏輯還是錯的，測試也可能剛好通過。這個測試宣告的是規則，所以只有當規則成立時它才會過。

💡 先讓這個測試保持失敗狀態。你接下來會用兩種方式修復它，而一個會失敗的測試，正是你用來驗證修復是否真的有效的最佳工具。

4. 解法 A：不要存它

如果數字是因為被存起來才過期，那就不要存它。等有人問的時候再算就好。

首先，把這個欄位從 struct 裡刪掉。就刪那一行。然後跑 cargo build，看看編譯器會說什麼： 

error[E0560]: struct `report::Report` has no field named `line_count`
  --> src/report.rs:23:13

error[E0609]: no field `line_count` on type `&report::Report`
  --> src/report.rs:28:50

兩個錯誤，兩個地方：一個是建立它的地方，一個是讀取它的地方。這就是編譯器在發揮它的強項。它沒辦法告訴你值是錯的，但只要你一刪掉欄位，它就會把所有依賴這個欄位的程式碼全部列出來。「刪掉東西然後讀錯誤訊息」，是找出誰在使用它的正當手法。

🔴 修改前 —— 一個曾經正確的數字
pub struct Report {
    pub content: String,
    pub line_count: usize,
}

pub fn new(filename: &str, content: String) -> Report {
    let line_count = content.lines().count();
    Report { /* ... */ line_count }
}

pub fn summary(&self) -> String {
    format!("{}：共 {} 行", self.filename, self.line_count)
}
🟢 修改後 —— 當場回答的問題
pub struct Report {
    pub content: String,
}

pub fn new(filename: &str, content: String) -> Report {
    Report { filename: filename.to_string(), content }
}

pub fn line_count(&self) -> usize {
    self.content.lines().count()
}

pub fn summary(&self) -> String {
    format!("{}：共 {} 行", self.filename, self.line_count())
}

把測試裡的 report.line_count 改成呼叫 report.line_count()，然後跑測試： 

test result: ok. 6 passed; 0 failed

notes.txt：共 4 行
空行 0 行，註解 0 行，程式碼 4 行

兩個數字都是 4 了。它們現在來自同一個源頭，所以永遠不會分岔。欄位會過期；但方法根本沒有東西可以過期。

5. 解法 B：留著它，並手動維護

另一個選擇是保留存起來的欄位，但要求每一個會修改 content 的方法都要負責更新它： 

pub fn add_title(&mut self) {
    let title = format!("=== {} ===\n", self.filename);
    self.content.insert_str(0, &title);
    self.line_count = self.content.lines().count();   // 新增這行
}

這招也行得通。測試過了，工具也印出 4 和 4。那麼，我們來模擬一下六個月後這份程式碼身上真實會發生的事 —— 有人加了第二個會修改 content 的方法： 

pub fn add_footer(&mut self) {
    self.content.push_str("=== end ===\n");
}

在 main.rs 裡，把它加在 add_title 旁邊，然後：

0 errors, 0 warnings
test result: ok. 6 passed; 0 failed

notes.txt：共 4 行
空行 0 行，註解 0 行，程式碼 5 行

Bug 原汁原味地回來了。乾淨的編譯、綠色的測試，但輸出卻是錯的。因為測試只知道 add_title，所以新方法就這麼大搖大擺地闖了過去。

如果你拿解法 A 來做同樣的實驗，數字會緊緊黏在一起 —— 5 和 5 —— 而且你完全不需要多寫任何一行程式碼。這就是值得你記住的差別：解法 B 需要人類在每次新增方法時，都靠意志力記住這件事。解法 A 則完全不需要記憶。

6. 所以該選哪一個？

這兩種做法在真實的 Rust 專案裡都會用到。Rust 官方教學（The Rust Book）在 AveragedCollection 的範例中，刻意教了解法 B：讓 add 和 remove 都去更新存好的平均值。那裡的重點是：解法 B 只有在欄位是私有（private），而且所有會改變來源的路徑都必須經過你控制的方法時，才是安全的。

這裡列出它們各自的代價，讓你自己選：

解法 A：重新計算 解法 B：快取並同步更新
每次呼叫的代價 每次都要掃過整個字串 只讀取一個 usize
新增方法的代價 無 多寫一行，而且要記得寫
失敗時的表現 變慢，但你可以測量出來 安靜且錯誤，而且測試抓不到
前提條件 無 私有欄位，嚴格控制的存取權限

對 hello_cli 來說，summary() 每次執行只會被呼叫一次，而且讀取的檔案通常一眨眼就掃完了，所以重新計算的代價你根本感覺不到。但如果這是一個每秒要被讀取數千次的 struct，權衡起來就不一樣了，這時你就會需要解法 B 加上私有欄位 —— 記住，絕對不要只寫快取而不做權限控制。

💡 閱讀的技能。當你打開一個陌生的 struct，試著尋找那些「可以從其他欄位推導出來」的欄位：集合旁邊的計數器、清單旁邊的總和、或是描述資料狀態的旗標。這每一個都是型別必須靠人工兌現的承諾 —— 當程式輸出不合理時，這絕對是你第一個該檢查的地方。

7. 檢查你記得多少

你選了解法 B。後來有人加了一個會修改 content 的方法，卻忘了寫更新快取的那一行。會發生什麼事？
閱讀一個陌生的 struct 時，哪一種欄位最值得你起疑心？
這一課的成果
你在自己的程式碼裡找到了一個真實的 Bug，寫了一個描述「為什麼這很重要」而不是「目前印出什麼」的測試，並用兩種方式修復它，同時看清了各自的代價。

你也學到了 Rust 的保證在哪裡止步。所有權和借用保護的是記憶體，它們不保護「意義」。帶有推導欄位的 struct 身上背負著一條規則，而這條規則只能靠你和你的測試來把關。
