Borrowing：看，但不拿走

目標：知道 & 和 &mut 各自在做什麼，看到 cannot borrow ... as mutable 這類訊息知道怎麼修，並且知道為什麼從 Lesson 4 開始就一直在寫 &。

你已經自己解出這一課了。

上一課的作業要求你用 clone 修好 E0382。你沒有。你寫的是這個： 

fn summarize(content: &String) {          // ← 這裡加了 &
    println!("共 {} 行", content.lines().count());
}

summarize(&content);                     // ← 這裡也加了 &
println!("{}", content);                 // ✅ 還能用

這就是編譯器在 E0382 底下提示的那條路：consider changing this parameter type ... to borrow instead。

這一課要補的是：這個 & 到底是什麼，以及它有什麼規則。

先講一個詞：引用

&content 不是 content 本身。它是一個指向 content 的東西。這個東西叫引用（reference）。

把引用交給函式，叫做借用（borrow）。

借用和移動的差別只有一件事：擁有者沒有變。 

let content = String::from("hello");

summarize(content);      // 移動：擁有者換成參數，content 失效
summarize(&content);     // 借用：擁有者還是 content，函式只是看一下

函式結束時，借來的引用消失，但字串不會被釋放 —— 因為引用從來沒有擁有它。上一課的第三條規則說「擁有者離開作用域時，值就被釋放」，借用者不是擁有者。

一個比喻：攤在桌上的筆記本

中文的「借」預設是借走 —— 借書、借錢，東西離開你手上。Rust 的 borrow 不是這個意思。

想成你把筆記本攤在桌上讓同事看。 

let mut notes = String::from("會議記錄");

review(&notes);        // 同事在旁邊看，只能看
edit(&mut notes);      // 同事拿筆在上面加一行

兩種情況筆記本都還在你桌上，都還是你的。差別只在同事能不能動筆。

真正把整本拿走的是移動： 

consume(notes);        // 筆記本被整本拿走，你桌上沒了

這才是中文語感的「借走」。但 Rust 不叫它 borrow，叫 move，而且它連還都不還。

三個詞的差別：
  • move —— 東西真的離開了，原本的變數失效
  • borrow（&） —— 東西沒動，只是給人看
  • mutable borrow（&mut） —— 東西沒動，但給人動筆
「借」在 Rust 裡的重點是會還，不是會走。

還你一筆從 Lesson 4 欠到現在的帳

Lesson 4 你寫過這一行，當時我只說「先照著寫」： 

for name in &names {
    println!("{}", name);
}

現在它可以解釋了。for 迴圈會消耗它跑過的東西。如果寫成 for name in names，整個 names 就被移動進迴圈，跑完就沒了 —— 迴圈後面再用 names 會是 E0382。

加上 &，迴圈只是借來看，names 還在。

同樣的，Lesson 8 的 &args[1] 也是借用 —— 你只想讀那個字串，不想把它從 args 裡搬出來。

需要改東西的時候：&mut

借來看是 &。借來改是 &mut。 

fn add_line(s: &mut String) {
    s.push_str("\n新的一行");
}

fn main() {
    let mut text = String::from("原本的內容");
    add_line(&mut text);
    println!("{}", text);          // 原本的內容 + 新的一行
}

三個地方都要寫 mut，少一個就編不過。少了 let mut 會是這樣： 

error[E0596]: cannot borrow `text` as mutable, as it is not declared as mutable
  |
5 |     let text = String::from("原本的內容");
6 |     add_line(&mut text);
  |              ^^^^^^^^^ cannot borrow as mutable
  |
help: consider changing this to be mutable
  |
5 |     let mut text = String::from("原本的內容");
  |         +++

這個錯誤訊息直接告訴你要加什麼、加在哪。照做就好。

兩條借用規則

在任何一個時間點，一個值可以有：
  • 任意多個 &（唯讀借用），或者
  • 剛好一個 &mut（可改借用）
兩者不能同時存在。

回到筆記本，這條規則就不是抽象規定了：

很多人可以同時看。五個人圍著看同一本筆記，沒問題 —— 反正沒人在改。

只能一個人動筆。兩個人同時在同一行寫字，會寫成一團亂。

有人在動筆的時候，別人不能看。這條最反直覺，但也最實際：他正在把第三頁撕下來重寫，你這時候讀第三頁，讀到的是半成品。

違反第一種： 

let mut text = String::from("hello");
let r1 = &text;                 // 借來看
text.push_str(" world");        // 同時想改
println!("{}", r1);             // 而且看的人還在用
error[E0502]: cannot borrow `text` as mutable because it is also borrowed as immutable
  |
3 |     let r1 = &text;
  |              ----- immutable borrow occurs here
4 |     text.push_str(" world");
  |     ^^^^^^^^^^^^^^^^^^^^^^^ mutable borrow occurs here
5 |     println!("{}", r1);
  |                    -- immutable borrow later used here

違反第二種： 

let mut text = String::from("hello");
let r1 = &mut text;
let r2 = &mut text;             // 第二個可改借用
println!("{} {}", r1, r2);
error[E0499]: cannot borrow `text` as mutable more than once at a time
  |
3 |     let r1 = &mut text;
  |              --------- first mutable borrow occurs here
4 |     let r2 = &mut text;
  |              ^^^^^^^^^ second mutable borrow occurs here

為什麼要有這兩條規則

回想上一課：String 可以增長。push_str 如果發現原本那塊記憶體不夠大，會另外找一塊更大的，把內容搬過去，然後把舊的釋放掉。

如果這時候有一個 & 還指著舊位置，它就指向一塊已經被釋放的記憶體。讀它會拿到垃圾，或是直接讓程式崩潰。

這叫資料競爭（data race）：兩個地方同時碰同一份資料，其中至少一個在改，而且沒有講好順序。

在 C++ 或 Go 裡，這種 bug 會在執行時出現，而且時機不固定，非常難查。Rust 在編譯時就擋掉。

這就是上一課那句話的完整版：Rust 把炸點從執行時搬到編譯時。

借用的範圍到「最後一次使用」為止，不是到大括號結尾。所以這段是合法的： 
let r1 = &text;
println!("{}", r1);             // r1 最後一次使用，借用在這裡結束
text.push_str(" world");        // ✅ 現在沒人在看了
把 E0502 那段的第 4、5 行對調就能編過。錯誤訊息裡的 immutable borrow later used here 指的就是這件事。

換你動手

在 hello_cli 上加一個會修改字串的函式。這次要用到 &mut。

目標：在印出檔案內容之前，先在最前面加一行標題。
  • 寫 fn add_title(content: &mut String, filename: &String)，讓它在 content 最前面插入一行 === 檔名 ===。（提示：String 有 insert_str(0, ...)。）
  • 在 Ok 那條分支呼叫它，然後印出 content。你會需要改 Ok(content) 那個綁定 —— 想一下要加什麼字。
  • 然後故意做錯：在呼叫 add_title 之前先寫 let peek = &content;，並且在呼叫之後才 println!("{}", peek);。跑一次，你應該看到 cannot borrow `content` as mutable because it is also borrowed as immutable。確認你能指出訊息裡哪一行是 immutable borrow later used here。
  • 最後把 peek 那兩行刪掉，讓程式跑通。

成功條件：cargo run -- notes.txt 印出標題行加上三行內容，而且沒給參數、給錯檔名這兩條路徑仍然不會 panic。

這一課的成果
Rust 記憶體模型最難的那一段結束了。你看到 cannot borrow ... 開頭的訊息時，知道它在講哪條規則被違反、以及怎麼修。所有權、移動、借用是三個連在一起的機制，你現在三個都懂了。這也是為什麼 Rust 不需要垃圾回收，卻仍然保證不會有 use-after-free 和資料競爭。從這裡開始，你看 Rust 程式碼裡滿滿的 & 不會再覺得是噪音 —— 每一個都在說「我只要看，不要拿走」。速查表：所有權與借用參考卡。

主要參考資料：The Rust Programming Language — 4.2 References and Borrowing（繁中版：rust-lang.tw）。想做練習題可以搭配 Rustlings 的 move_semantics 後半段。
