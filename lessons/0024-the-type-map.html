Lesson 0024 · Rust · CLI 工具養成路線

型別地圖：標準庫給了你哪些容器，為什麼要分這麼細

學習目標：建立一套「看到陌生型別就能定位它」的方法。學完你要能對任何一個型別回答三個問題：誰擁有資料、大小固不固定、能不能改 —— 並且知道 Rust 為什麼不肯只給你一種容器。

1. 你會卡在哪

你打開一個沒看過的 Rust 檔案，函式簽名長這樣： 

fn render(items: &[Item], index: &BTreeMap<String, usize>) -> Result<String, Box<dyn Error>>

你認得 String、usize、Result。但另外那些是什麼？

更麻煩的是你分不出來哪些是重點、哪些只是雜訊。&[Item] 跟 Vec<Item> 差在哪，是無關緊要的寫法差異，還是作者刻意的決定？BTreeMap 為什麼不是 HashMap？

沒有地圖的時候，你只能一個一個查，查完也串不起來。這一課要給你的不是一張型別清單 —— 是一個能自己推出答案的框架。

2. 一切的分水嶺：編譯器需要知道「你要佔多大位子」

Rust 之所以會設計出這麼多種容器，背後的根本原因只有一個：編譯器在打包程式時，必須精準知道每個變數需要多大的記憶體空間。

這就像是安排劇院座位，你必須先告訴售票員你需要幾個位子，他才能幫你劃位。編譯器要產生機器碼時，也必須預先劃好記憶體空間。

我們可以眼見為憑。呼叫 std::mem::size_of，就能直接看穿各個型別的「真實體積」（單位是位元組）： 

use std::mem::size_of;

fn main() {
    println!("{}", size_of::<[i32; 3]>());  // 12
    println!("{}", size_of::<Vec<i32>>());  // 24
    println!("{}", size_of::<String>());    // 24
    println!("{}", size_of::<&str>());      // 16
    println!("{}", size_of::<&i32>());      //  8
}

這些數字背後，藏著 Rust 處理資料的秘密：

  • [i32; 3] 佔 12 位元組。因為它實實在在地裝了三個 i32（每個 4 位元組）。資料本體就安安穩穩地躺在那裡。
  • Vec<i32> 佔 24 位元組，而且不管裡面裝三個還是三百萬個，都是 24。為什麼？因為 Vec 本身不裝真實資料，它只是一個「遙控器」，裡面記錄了三件事：資料在哪裡（指標，8 位元組）、現在裝了幾個（長度，8 位元組）、最多可以裝幾個（容量，8 位元組）。真正的資料被放在記憶體的另一個角落（堆積，Heap）。
  • String 也是 24 位元組，理由完全相同。在底層，String 其實就是一個確保內容是合法 UTF-8 文字的 Vec<u8>。
  • &str 佔 16 位元組。它包含一個指標和一個長度，沒有容量。因為它只是一個「借來看的視窗」，不能隨意擴充大小。

因此，當我們說「大小固定」時，要釐清是誰的大小：Vec 這個變數本身的大小是永遠固定的（24 位元組），所以編譯器能輕易幫它劃位；而它所指向的內容則是可變的。這就是為什麼它能被放在固定大小的空間裡，卻能擁有無限擴充的魔力。

💡 TypeScript 對照：在 JS 裡，所有的物件和陣列都是「遙控器」（引用型別），真實資料一律丟到堆積（heap）上，你不需要也無法干涉。但 Rust 把選擇權交給你：你要把資料直接塞在原地（[i32; 3]），還是把資料放遠一點，原地只留一個遙控器（Vec<i32>）？這份多出來的選擇權，就是 Rust 型別看起來這麼多的原因。

當編譯器算不出大小時，它會直接罷工

這絕不是紙上談兵。如果你寫出一個讓編譯器算不出大小的型別，它會當場報錯： 

enum List {
    Node(i32, List),   // 俄羅斯娃娃：一個 List 裡面又包著一個 List
    End,
}

編譯器會這樣抱怨： 

error[E0072]: recursive type `List` has infinite size
  |
2 |     Node(i32, List),
  |               ---- recursive without indirection
  |
help: insert some indirection (e.g., a `Box`, `Rc`, or `&`) to break the cycle
  |
2 |     Node(i32, Box<List>),

infinite size（無限大小）—— 因為 List 裡面有 List，編譯器在計算體積時陷入了無窮迴圈。但它很貼心地給了解法：包一層 Box。Box 的魔法在於「把龐大的資料搬到別處，原地只留下一個大小永遠是 8 位元組的指標」。

關於 Box 的詳細用法我們會在第 30 課深入探討。現在你只需要記住這個核心觀念：當資料大小無法預測時，就用一層指標（像 Box 或 &）把它變成固定大小。

3. 三個問題，定位任何型別

這是這一課真正要你帶走的東西。看到任何陌生型別，問三個問題：

問題 看什麼 例子
誰擁有這份資料？ 開頭有沒有 &。有就是借來的，用完要還，你不能決定它的生死。 String 擁有；&str 借用
數量能不能變？ 是不是寫死在型別裡。方括號裡有數字就是寫死的。 [i32; 3] 固定三個；Vec<i32> 可增可減
能不能改？ mut 或 &mut。兩者都沒有就是唯讀。 &[i32] 只能讀；&mut [i32] 可以改

拿開場那個簽名試一次： 

fn render(items: &[Item], index: &BTreeMap<String, usize>) -> ...
  • &[Item]：借來的、一串 Item、不能改。所以 render 只是要讀過去，不會動到你的資料，也不會把它拿走。
  • &BTreeMap<String, usize>：借來的、鍵是 String 值是 usize 的對應表、不能改。

你還不知道 Item 是什麼、也不知道 render 在做什麼。但你已經知道這個函式不會偷走或破壞你的東西。這件事光看簽名就成立，不用翻實作。

4. 為什麼是 &[Item] 而不是 &Vec<Item>

這是你讀 Rust 會一直遇到的一組。&[T] 叫做 slice（切片）：一段連續資料的視窗，只有「從哪開始」和「有幾個」。

差別在於誰能傳進來： 

fn total(nums: &[i32]) -> i32 {
    nums.iter().sum()
}

fn main() {
    let arr: [i32; 3] = [1, 2, 3];
    let vec: Vec<i32> = vec![1, 2, 3];

    println!("{}", total(&arr));  // 6
    println!("{}", total(&vec));  // 6
}

同一個函式，陣列和 Vec 都吃得下。如果參數寫成 &Vec<i32>，陣列那行就會編譯失敗。

所以慣例是：參數收 &[T]，回傳給 Vec<T>。收的時候放寬，給的時候給完整的所有權。

&str 和 String 就是這組關係的字串版本。&str 是 &[u8] 的文字版，String 是 Vec<u8> 的文字版。第 12 課那個「參數收 &str」的建議，跟這裡是同一條規則。詳見 字串型別參考卡。

5. 型別地圖

標準庫的容器就這些，數量不多：

型別 做什麼 什麼時候用它
Vec<T> 可增長的序列，有順序，可用索引 預設選項。不確定用什麼就用它
&[T] Vec 或陣列的唯讀視窗 函式參數。讓呼叫端有更多選擇
[T; N] 長度寫死在型別裡的陣列 數量真的永遠固定，例如 RGB 三個值
String / &str 擁有的文字 / 借來的文字 同上一組的關係
HashMap<K, V> 鍵找值，最快，沒有順序 只在乎查得快，輸出順序無所謂
BTreeMap<K, V> 鍵找值，永遠按鍵排序 要照順序輸出，或要找「範圍內的鍵」
HashSet<T> 只記有沒有，自動去重 「這個看過了嗎」、去掉重複
VecDeque<T> 頭尾兩端都能快速進出 佇列、需要 push_front 的時候
Option<T> 有一個 T，或什麼都沒有 值可能不存在，而且不存在是正常的
Result<T, E> 成功帶 T，失敗帶 E 操作可能失敗，而且失敗要說明原因
Box<T> 把 T 放遠一點，這裡留指標 大小算不出來的時候（第 30 課）

Option 和 Result 你已經在用了。把它們放進這張表，是因為它們跟其他的是同一類東西 —— 包住別的型別、並且附帶一個規則的容器。Vec 附帶的規則是「有很多個」，Option 附帶的規則是「可能沒有」。形式上沒有高下之分。

6. 為什麼要分這麼細

因為每一個都是一組取捨，而 Rust 不幫你選。

最好的示範是 HashMap 跟 BTreeMap。介面幾乎一樣，行為差一件事： 

use std::collections::{BTreeMap, HashMap};

fn main() {
    let mut h: HashMap<&str, i32> = HashMap::new();
    let mut b: BTreeMap<&str, i32> = BTreeMap::new();

    for (k, v) in [("pear", 1), ("apple", 3), ("mango", 2), ("kiwi", 5)] {
        h.insert(k, v);
        b.insert(k, v);
    }

    println!("{:?}", h.keys().collect::<Vec<_>>());
    println!("{:?}", b.keys().collect::<Vec<_>>());
}

我連續跑了三次，這是真實輸出： 

HashMap  keys: ["pear", "apple", "kiwi", "mango"]
BTreeMap keys: ["apple", "kiwi", "mango", "pear"]

HashMap  keys: ["apple", "kiwi", "mango", "pear"]
BTreeMap keys: ["apple", "kiwi", "mango", "pear"]

HashMap  keys: ["apple", "mango", "kiwi", "pear"]
BTreeMap keys: ["apple", "kiwi", "mango", "pear"]

BTreeMap 三次都一樣。HashMap 三次都不同 —— 第二次剛好排序了，那是巧合，不是保證。

代價在哪：BTreeMap 為了維持順序，插入和查詢都比 HashMap 慢一些。所以這不是「BTreeMap 比較好」，是兩個不同的東西，你要自己決定要哪一個。

HashSet 的存在也是同一個邏輯 —— 當你只在乎「有沒有」的時候，值那一欄是浪費的： 

use std::collections::HashSet;

fn main() {
    let mut seen: HashSet<&str> = HashSet::new();

    println!("{}", seen.insert("apple"));  // true  ← 第一次，是新的
    println!("{}", seen.insert("apple"));  // false ← 已經有了
    println!("{}", seen.len());            // 1
}

insert 回傳 bool 告訴你「這是不是第一次看到」。要判斷重複，這一行就夠了。

💡 跟 TypeScript 的差別在哪：JS 也有 Map 和 Set，概念一樣。但 JS 沒有 BTreeMap／VecDeque 這種層級的選擇，因為 JS 的設計哲學是「給你一個夠用的，細節引擎處理」。Rust 的哲學相反：把取捨攤在型別上，讓你在寫的時候就選好。所以型別看起來變多了，但每一個都在替你記住一個決定 —— 這也是為什麼讀 Rust 的時候，型別本身就是資訊。

7. 角括號裡的那個字母

Vec<T>、Option<T>、HashMap<K, V> —— 這些大寫字母是泛型參數，意思是「這裡填什麼型別都行，你填了我就記住」。

跟 TypeScript 完全一樣：

TypeScript

const xs: Array<string> = [];
xs.push("a");
xs.push(1);  // 型別錯誤

Rust

let mut xs: Vec<String> = Vec::new();
xs.push("a".to_string());
xs.push(1);  // 型別錯誤

T 只是慣用的名字（type），K／V 是 key／value。名字沒有魔力，換成別的字母也一樣。

怎麼自己寫出帶 <T> 的函式和型別，是第 27 課的內容。這一課只要能讀懂就好：看到角括號，先把它當成「這個容器裡裝的是什麼」。

小測驗一：為什麼 size_of::<Vec<i32>>() 不管裡面裝幾個元素，答案都是 24？
小測驗二：函式參數寫 &[i32] 而不寫 &Vec<i32>，得到的好處是什麼？
小測驗三：你要輸出一份「詞 → 次數」而且要求每次執行順序都一樣。哪個選擇最直接？

換你動手

這一課有兩個練習。第一個是驗證，第二個是把新知識裝回 hello_cli。

練習一：先猜，再跑。
  1. 在任何地方開一個 types.rs，把上面第 2 節的 size_of 程式、第 6 節的 HashMap／BTreeMap 程式、還有 HashSet 程式抄進同一個 main。
  2. 執行前先在紙上（或註解裡）寫下你猜的每一行輸出。這一步不能跳 —— 猜錯的地方才是你真正學到東西的地方。
  3. rustc types.rs && ./types，對答案。
  4. 額外試一件事：把 size_of::<Vec<i32>>() 改成 size_of::<Vec<String>>()。猜猜看數字會不會變，然後驗證你的猜測。
練習二：把 word_counts 換成 BTreeMap。
  1. report.rs：把 use std::collections::HashMap; 換成 BTreeMap，word_counts 的回傳型別和 HashMap::new() 也一起換。entry().or_insert() 那行完全不用動 —— 兩者的介面是一樣的。
  2. main.rs：--words 那一段現在可以簡化。BTreeMap 走訪本來就有序，所以 collect 成 Vec 再 sort() 的那兩行可以刪掉，直接 for (word, count) in counts。
  3. cargo test：五個測試應該全過，一行都不用改。想一下為什麼 —— 測試只用了 .get() 和 .len()，那是兩者共通的介面。
💡 別誤會這個練習的意思。不是說 BTreeMap 比較好，所以 23 課教錯了。collect + sort 那條路你還是需要 —— 一旦你想改成按次數排序（次數多的在前），BTreeMap 就幫不上忙了，因為它只排鍵。這個練習要你體會的是：選對型別，程式碼會自己變短；選錯，你就得手動補上那個型別本來會給你的東西。

驗證條件：

指令 預期
cargo test 5 passed，且你沒有改動任何測試
cargo run -- --words words.txt apple 3 / banana 2 / cherry 1，跟換之前一模一樣
cargo run -- notes.txt 沒受影響
這一課的成果
你有一個框架了。看到陌生型別，問三件事：誰擁有、大小固不固定、能不能改。這三個問題能定位標準庫裡幾乎每一個容器，之後也能定位別人自訂的型別。

更重要的是那個「為什麼」：Rust 的型別之所以多，是因為它把取捨攤開來讓你選，而不是替你決定。所以在 Rust 裡，型別本身就攜帶資訊 —— 作者選了 BTreeMap 而不是 HashMap，那是一個決定，不是隨手寫的。讀 code 的時候這件事會一直幫到你。
