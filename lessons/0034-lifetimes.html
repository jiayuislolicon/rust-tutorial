Lifetime — 編譯器怎麼知道 reference 活多久

學習目標：word_counts() 每次被呼叫，都會用 .to_string() 把每個字複製一份。但那些字本來就住在 self.content 裡——如果能直接借成 &str，就能省掉所有多餘的記憶體配置。這一課你會把 map 的 key 改成借用，並理解編譯器怎麼確認：那些借來的 reference 不會活得比來源更久。

1. 複製 vs 借用

打開 hello_cli/src/report.rs，找到 word_counts()： 

pub fn word_counts(&self) -> BTreeMap<String, usize> {
    let mut counts = BTreeMap::new();
    for word in self.content.split_whitespace() {
        *counts.entry(word.to_string()).or_insert(0) += 1;
    }
    return counts;
}

split_whitespace() 產生的每個 word 本來就是 &str——指向 self.content 裡那段文字的一個 reference。但你把它 .to_string() 了：配置一塊新記憶體、把字元複製過去。對一份一千行的檔案來說，這是上千次不必要的配置。

如果 map 的 key 改成 &str，直接指向 self.content 裡的片段，就能零配置： 

pub fn word_counts(&self) -> BTreeMap<&str, usize> {
    let mut counts = BTreeMap::new();
    for word in self.content.split_whitespace() {
        *counts.entry(word).or_insert(0) += 1;
    }
    counts
}

改了兩件事：回傳型別從 BTreeMap<String, usize> 變成 BTreeMap<&str, usize>，.to_string() 也刪掉了。跑 cargo build——能編譯，測試也過。看起來只是換了一個型別，但編譯器背後多做了一件事：它開始追蹤那些 &str 能活多久。

2. 那些 &str 指向誰的記憶體？

對你來說，回傳的 map 只是「字串片段 → 次數」的對照表。但對編譯器來說，map 裡的每個 key 都是一個 reference——它必須確認那些 reference 指向的記憶體，在 map 被使用的整段時間裡都還有效。如果 Report 被 drop，或者 content 被改掉，那些 reference 就會指向已經不存在的記憶體。編譯器不允許這件事發生；它會用 lifetime 來追蹤每個 reference 能活多久。

實際上編譯器會替你推導出這個 lifetime，寫成 'a。它看到函式簽名只有一個 reference 輸入（&self），就套用一條叫做 lifetime elision（省略規則）的推論：「輸出裡所有的 reference，都活得跟 &self 一樣久。」

如果把省略的 lifetime 寫出來，簽名長這樣：

pub fn word_counts<'a>(&'a self) -> BTreeMap<&'a str, usize>

'a 是一個標籤，唸作「lifetime a」。它的意思是：回傳 map 裡的 &str 借的記憶體，來自 &self 所指向的那個 Report——只要那個 Report 還活著，這些 reference 就有效。

  • &str → 「我借了一段文字」
  • &'a str → 「我借了一段文字，而且這段借用的有效期間叫做 'a」

你不需要手寫這段——省略規則已經替你推導了。但知道它藏在簽名裡，你就能看懂編譯器報錯時在講什麼。

3. 省略規則失效的情況

省略規則只在少數明確的情況下有效。最常見的失敗場景是：函式有兩個以上的 reference 輸入，編譯器無法判斷輸出該跟哪一個綁在一起。這時它就不會替你猜——它會要你自己說清楚。

來寫一個取兩行中較長的那行的函式，看看會發生什麼：

fn longer_line(a: &str, b: &str) -> &str {
    if a.len() >= b.len() { a } else { b }
}

編譯器拒絕，訊息是：

error[E0106]: missing lifetime specifier
 --> src/report.rs
  |
  | fn longer_line(a: &str, b: &str) -> &str {
  |                   ----     ----     ^ expected named lifetime parameter
  |
  = help: this function's return type contains a borrowed value,
          but the signature does not say whether it is borrowed from `a` or `b`

編譯器不是在問你「這個 reference 活多久」——它是在問：「回傳值借自 a 還是 b？」這兩種情況的 lifetime 可能不同，所以你不能省略。你必須自己標出來： 

fn longer_line<'a>(a: &'a str, b: &'a str) -> &'a str {
    if a.len() >= b.len() { a } else { b }
}

三個位置都標 'a，意思是 a、b 和回傳值共享同一段有效區間。呼叫這個函式的人，必須確保 a 和 b 都在這段區間內是活的——編譯器會在呼叫端驗證這件事。

4. struct 裡面的 reference

函式可以回傳 reference，struct 也可以存 reference——邏輯是一樣的。如果你想把一個 &str 放進 struct，比如一個「帶有分類的行」： 

struct ClassifiedLine {
    text: &str,
    kind: LineKind,
}

一樣會得到 missing lifetime specifier。修法和函式一樣：加一個 lifetime 參數： 

struct ClassifiedLine<'a> {
    text: &'a str,
    kind: LineKind,
}

意思是：一個 ClassifiedLine 只能活到它借的那段文字還活著為止。如果你試圖讓它活得比來源更久，編譯器會拒絕。

這裡我們不需要把這個 struct 加進專案——理解這個模式就夠了。之後碰到需要在 struct 裡存放 reference 的情況，你就知道為什麼編譯器要求 <'a>。

5. 三條省略規則

到這裡你可能會想：編譯器到底什麼時候會替你推導、什麼時候不會？編譯器在你沒寫 lifetime 的時候，會依序嘗試以下三條規則；如果三條都套完了，還有某個輸出的 reference 沒被指定 lifetime——它就報錯。

  • 規則一：每個 reference 參數各得到自己的 lifetime。
    fn f(a: &str, b: &str) 被看成 fn f<'a, 'b>(a: &'a str, b: &'b str)。
  • 規則二：如果剛好只有一個 reference 輸入，輸出的所有 reference 都用它的 lifetime。
    fn f(s: &str) -> &str 被看成 fn f<'a>(s: &'a str) -> &'a str。
  • 規則三：如果有 &self 或 &mut self，輸出用 self 的 lifetime。
    這就是 word_counts(&self) 能通過編譯的原因——規則三直接套用了。

回頭看 longer_line(a: &str, b: &str) -> &str 為什麼失敗：規則一給了兩個不同的 lifetime（'a 和 'b），規則二不適用（有兩個 reference 輸入），規則三也不適用（沒有 &self）。三條規則都套完，但輸出的 lifetime 還是無法確定——所以報錯。

6. 動手改 word_counts()

前面你已經看過改動長什麼樣子。現在回到 hello_cli/src/report.rs，把 word_counts() 正式改成借用版本：

🔴 修改前 —— 每個字都 clone 成 String
pub fn word_counts(&self) -> BTreeMap<String, usize> {
    let mut counts = BTreeMap::new();
    for word in self.content.split_whitespace() {
        *counts.entry(word.to_string()).or_insert(0) += 1;
    }
    return counts;
}
🟢 修改後 —— reference 直接指向 content
pub fn word_counts(&self) -> BTreeMap<&str, usize> {
    let mut counts = BTreeMap::new();
    for word in self.content.split_whitespace() {
        *counts.entry(word).or_insert(0) += 1;
    }
    counts
}

main.rs 不需要改——&str 跟 String 一樣能用 {} 印出來。跑 cargo test，確認測試都通過。

7. 檢查你記得多少

你把 word_counts() 從複製改成借用，省掉了上千次 .to_string() 的記憶體配置。

你也學到了 Rust 怎麼用 lifetime 追蹤每個 reference 的有效範圍——大多數時候省略規則會替你推導；但碰到多個 reference 輸入，或在 struct 裡存放 reference 時，你得手寫標注。

核心觀念只有一個：lifetime annotation 是給編譯器看的標籤，告訴它「這些 reference 來自同一個來源，不會活得比來源更久」。
