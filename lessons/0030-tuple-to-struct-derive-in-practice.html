Tuple 變 struct：把 #[derive] 裝進你的專案

學習目標：你的 count_kinds() 回傳一個 bare tuple，三個數字全靠位置來區分。你會親自證明這種寫法能出錯、卻不會被編譯器攔住，然後用一個帶 #[derive] 的 struct 取代它，把「第幾個是什麼」寫進型別裡。

1. 位置決定意義，沒人幫你記

打開 hello_cli/src/report.rs，找到 count_kinds 回傳的那一行： 

pub fn count_kinds(&self) -> (usize, usize, usize) {
    // ...
    (empty_counts, comment_counts, code_counts)
}

現在假設你手滑，把回傳值的順序打亂了： 

(code_counts, comment_counts, empty_counts)

跑一下 cargo test：全部通過。來看看那個測試為什麼抓不到： 

let counts = report.count_kinds();
assert_eq!(counts, (1, 1, 1));

三個值剛好都是 1。不管你怎麼交換順序，(1, 1, 1) 永遠等於自己。測試抓不到，不代表呼叫端就安全。在 main.rs 裡你寫的是： 

let (empty, comment, code) = report.count_kinds();

這些名字是呼叫端自己取的。對型別系統來說，這只是三個 usize 排成一排——它不知道第一個應該代表「空行」。順序寫反了也不會報錯；錯誤的數字會被靜靜地塞進錯誤的變數名裡。

⚠️ 函式回傳多個同型別的值、卻靠位置區分意義，這是一種編譯器幫不了你的 bug。手滑交換順序時，它不會有任何意見。

2. 命名欄位：把位置資訊寫進型別裡

解法是把位置資訊寫進型別：用 struct，讓每個欄位有自己的名字。 

#[derive(Debug, PartialEq)]
pub struct LineStats {
    pub empty: usize,
    pub comment: usize,
    pub code: usize,
}

這個 struct 需要 #[derive(Debug, PartialEq)]——Lesson 29 學過的那兩個。Debug 讓 {:?} 可用，測試失敗時能印出結構；PartialEq 讓 == 可用，assert_eq! 才能比較兩個 struct。少了任何一個，等一下的測試都編不過。

PartialEq 能 derive，是因為三個欄位都是 usize，而 usize 本身已經有 PartialEq。這就是 Lesson 29 提過的規則：型別裡每個欄位也必須實作那個 trait，derive 才合法。

3. 把 count_kinds 換成 line_stats

先把函式簽名改成回傳 LineStats，而不是 tuple：

🔴 修改前
pub fn count_kinds(&self) -> (usize, usize, usize) {
    // ...
    (empty_counts, comment_counts, code_counts)
}
🟢 修改後
pub fn line_stats(&self) -> LineStats {
    let empty = self.content.lines()
        .filter(|line| matches!(Report::classify_line(line), LineKind::Empty))
        .count();

    let comment = self.content.lines()
        .filter(|line| matches!(Report::classify_line(line), LineKind::Comment))
        .count();

    let code = self.content.lines()
        .filter(|line| matches!(Report::classify_line(line), LineKind::Code))
        .count();

    LineStats { empty, comment, code }
}

回傳的 LineStats { empty, comment, code } 用了欄位縮寫：變數名稱和欄位名稱相同時，empty: empty 可以縮成 empty。你在 Report::new 裡用過同樣的寫法——content 那一行就是。

4. 測試：struct literal 當預期值

把測試改成這樣： 

#[test]
fn line_stats() {
    let report = Report::new("test.txt", "code\n\n// comment\n".to_string());
    let stats = report.line_stats();

    assert_eq!(
        stats,
        LineStats {
            empty: 1,
            comment: 1,
            code: 1,
        }
    );
}

現在你可以看著 empty: 1, comment: 1, code: 1 確切知道每個數字指的是什麼。假如 line_stats() 裡面有人把 empty 和 code 寫反，編譯器不會擋——但測試資料一旦不同（比如 empty: 2, comment: 0, code: 3），失敗訊息會直接指出哪個欄位對不上。

另一個測試也更直觀了：

#[test]
fn summary_agrees_with_line_stats() {
    let mut report = Report::new("t.txt", "a\nb\nc\n".to_string());
    report.add_title();

    let stats = report.line_stats();
    assert_eq!(report.line_count(), stats.empty + stats.comment + stats.code);
}

stats.empty + stats.comment + stats.code 讀起來像一句話。counts.0 + counts.1 + counts.2 則得對照位置編號才知道每個數字是什麼。

5. 更新 main.rs

main.rs 也要跟著改。原本用 tuple destructuring 取值：

🔴 修改前
let (empty, comment, code) = report.count_kinds();
println!("空行 {} 行，註解 {} 行，程式碼 {} 行", empty, comment, code);
🟢 修改後
let stats = report.line_stats();
println!(
    "空行 {} 行，註解 {} 行，程式碼 {} 行",
    stats.empty, stats.comment, stats.code
);

印出來的結果跟以前一樣，但保障不同了。如果有人改了 LineStats 的欄位名稱，所有用到它的地方——包括這裡——都會報 error[E0609]: no field ... on type LineStats。位置對換不再是沉默的 bug，而是編譯器會直接擋下來的錯誤。

跑 cargo test 確認全部通過，然後繼續看 derive 的限制。

6. 不是每個型別都能 derive 所有 trait

LineStats 的三個欄位都是 usize，derive 順利通過。但並非每個型別都這麼配合。打開 hello_cli/src/errors.rs，AppError 目前沒有任何 derive。先加上 Debug 試試： 

#[derive(Debug)]
pub enum AppError {
    ReadFailed(std::io::Error),
    Empty,
    UnknownFlag(String),
    MissingValue(String),
    BadNumber(std::num::ParseIntError),
}

編譯通過——io::Error、String、ParseIntError 各自都有 Debug，所以整個 enum 也能 derive。加完之後你可以用 format!("{:?}", error) 印出任何一個 variant 的結構，方便除錯。

同樣的邏輯，PartialEq 應該也行吧？試著加上去： 

#[derive(Debug, PartialEq)]
pub enum AppError { ... }

編譯器拒絕了： 

error[E0277]: can't compare `std::io::Error` with `std::io::Error`
   --> src/errors.rs
    |
    | #[derive(Debug, PartialEq)]
    |                 ^^^^^^^^^ the trait `PartialEq` is not implemented for `std::io::Error`

問題出在 io::Error：它沒有 PartialEq。兩個「找不到檔案」的錯誤實例不應該被當作相等——它們可能指的是不同的檔案、不同的瞬間。一個欄位缺了這個 trait，整個 enum 就跟著 derive 不了。

所以 AppError 最終只留 #[derive(Debug)]。這和 Display 不能 derive（Lesson 29）是同一條規則的兩面：derive 只能產生「從結構就能唯一決定的實作」。某個欄位拿不出那份實作，整個型別就無法自動取得它。

你把一個靠位置辨認的 tuple 換成了有名字的 struct，加上 #[derive(Debug, PartialEq)] 讓它能直接用在 assert_eq! 裡。你也親眼看到了 derive 的限制：AppError 裡的 io::Error 擋住了 PartialEq，因為 derive 只能在每個欄位也具備那個 trait 的前提下產生 impl。

回頭看整條路：Lesson 28 教你讀 trait bound（T: PartialEq + Debug），Lesson 29 教你用 #[derive] 把那些 trait 裝上去。這一課把兩件事接在一起，直接改進了你自己的程式碼。
