用 cargo test 寫單元測試

學習目標：學會用 #[test] 與 assert_eq! 幫 report.rs 裡的邏輯寫自動化測試，並理解 #[cfg(test)] 如何讓測試程式碼不進入正式編譯結果。

1. 為什麼要寫測試？

到目前為止，你驗證程式是否正確的方法，是手動執行 cargo run -- notes.txt、換一個不存在的檔名再跑一次、再換一個空檔案跑第三次，然後用眼睛檢查輸出對不對。這個流程沒有錯，但有兩個問題：每次改完程式碼都要重複做一次，而且只有你自己記得該測哪些情況。

測試把這個手動流程變成程式碼本身的一部分。你把「這個函式在這個輸入下應該回傳什麼」寫成一段程式，之後每次執行 cargo test，這些檢查都會自動重跑一次。改壞了什麼，測試會直接告訴你，不用再靠肉眼比對終端機輸出。

💡 對照 TypeScript：如果你用過 Jest 或 Vitest，這裡的 #[test] 就相當於 test('...', () => { ... })，assert_eq!(a, b) 就相當於 expect(a).toBe(b)。核心概念一樣：寫一段「呼叫函式、檢查結果」的程式碼，交給測試工具批次執行。

2. #[test] 與 assert_eq!

一個測試就是一個標了 #[test] 的函式，裡面用 assert_eq!（或 assert!）檢查某個值是否符合預期： 

#[test]
fn two_plus_two_is_four() {
    assert_eq!(2 + 2, 4);
}
  • #[test]：告訴 cargo test「這個函式是一個測試，請執行它」。一般函式不會被自動執行，加了這個標記才會。
  • assert_eq!(左, 右)：檢查兩個值是否相等。相等就什麼事也不會發生，測試通過；不相等，這個函式會 panic，測試被標記為失敗，並印出兩邊實際的值方便你比對。
  • assert!(條件)：檢查一個布林值是否為 true。false 一樣會 panic 並讓測試失敗。

3. #[cfg(test)] mod tests：測試放哪裡

Rust 的慣例是把測試寫在同一個檔案裡，放進一個獨立的 mod tests，並在上面標 #[cfg(test)]： 

// report.rs 的最下方

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn two_plus_two_is_four() {
        assert_eq!(2 + 2, 4);
    }
}
  • #[cfg(test)]：告訴編譯器「只有在執行 cargo test 時才編譯這段程式碼」。執行 cargo build 或 cargo run 時，這個 mod 完全不存在，正式的執行檔不會多帶任何測試程式碼的重量。
  • use super::*;：tests 是 report 模組裡面的一個子模組，這行把外層（report.rs 本身）的所有項目都引入進來，這樣測試才能直接呼叫 Report::classify_line 之類的東西，不用寫更長的路徑。

4. 執行 cargo test

在專案目錄下執行 cargo test，Cargo 會編譯所有標了 #[test] 的函式並依序執行，最後印出一份總結： 

running 1 test
test report::tests::two_plus_two_is_four ... ok

test result: ok. 1 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out

如果某個測試的 assert_eq! 失敗，那一行會顯示 FAILED，下方會印出失敗的斷言、左右兩邊實際的值，以及發生在哪一行——跟一般 panic 的錯誤訊息長得一樣，只是被 cargo test 攔下來歸類成「這個測試沒過」，而不會讓整個指令直接中斷。

小測驗一：assert_eq!(1 + 1, 3) 這行程式碼在測試裡執行後，會發生什麼事？
小測驗二：如果拿掉 mod tests 上方的 #[cfg(test)]，執行 cargo run 時會有什麼差異？

換你動手

幫 report.rs 補上三個測試：
  1. 在 report.rs 檔案最下方，加上 #[cfg(test)] mod tests { use super::*; ... }。
  2. 測試 Report::classify_line：分別傳入空字串 ""、註解 "// hi"、一般程式碼 "let x = 1;"，用 assert!(matches!(結果, LineKind::Empty)) 這種寫法確認回傳的變體正確（matches! 是用來判斷一個值是否符合某個 enum 變體的巨集，之後會有更完整的說明）。
  3. 測試 count_kinds：用 Report::new("test.txt", "code\n\n// comment\n".to_string()) 建一個 Report，呼叫 count_kinds()，用 assert_eq!(結果, (1, 1, 1)) 確認三個計數都正確。

驗證條件：執行 cargo test，三個測試都顯示 ok。接著故意把某個測試的期望值改錯（例如把 (1, 1, 1) 改成 (2, 1, 1)），確認 cargo test 會顯示 FAILED 並印出實際與期望值的差異——這一步是為了親眼確認測試真的有在檢查東西，不是隨便都顯示 ok。改完記得把期望值改回正確答案。

這一課的成果
report.rs 裡的核心邏輯（分類每一行、統計空行/註解/程式碼數量）現在有自動化測試守著。以後修改 classify_line 或 count_kinds 的邏輯，只要跑一次 cargo test，就知道有沒有改壞原本的行為，不用再手動跑三次 cargo run 肉眼比對。
