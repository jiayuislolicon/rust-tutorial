疊代器：filter / map / count

學習目標：學會用 .filter()、.map()、.count() 取代手寫的 for 迴圈與計數變數，並用上一課寫的測試當安全網，確認重構後行為完全沒變。

1. 你已經在用疊代器了

report.rs 裡的 self.content.lines()，回傳的就是一個疊代器（iterator）。

疊代器是一個「可以一個一個吐出元素」的東西。它本身不是集合，也不會先把所有元素算好放在記憶體裡。你每跟它要一個，它才算一個。

你目前的用法是把它交給 for 迴圈，讓迴圈一路跑到底。但疊代器還可以先接上其他步驟再收尾，這就是這一課要學的。

💡 對照 TypeScript：這組方法跟 JS 陣列的 arr.filter(...)、arr.map(...)、arr.length 幾乎是一對一的。 最大的差別是 JS 每一步都產生一個新陣列，Rust 的每一步只是在描述「等一下要做什麼」，還沒真的跑。

2. 三個方法

先看一個純數字的例子：

let numbers = vec![1, 2, 3, 4, 5, 6];

let even_count = numbers.iter().filter(|n| *n % 2 == 0).count();

println!("{}", even_count); // 3
  • .iter()：從一個集合（這裡是 Vec）做出疊代器。 lines() 已經直接給你疊代器了，所以不需要再呼叫 .iter()。
  • .filter(條件)：只留下讓條件為 true 的元素。 括號裡的 |n| ... 是閉包（closure），等同 TS 的 (n) => ...。
  • .map(轉換)：把每個元素換成另一個值，數量不變。
  • .count()：把疊代器跑到底，回傳跑過幾個元素。

3. 惰性：接上步驟，跟真的執行，是兩件事

.filter() 和 .map() 不會執行任何東西。它們只是回傳一個「包了一層額外規則」的新疊代器。

真正讓它動起來的是最後那個收尾的方法，例如 .count()、.collect()，或是一個 for 迴圈。這種特性叫惰性（lazy）。 

let numbers = vec![1, 2, 3];

let step = numbers.iter().map(|n| n * 2); // 這一行不會做任何乘法

let doubled: Vec<i32> = step.collect(); // 到這裡才真的算，得到 [2, 4, 6]
  • .collect()：把疊代器跑到底，把結果收成一個集合。 它需要你講清楚要收成什麼型別，所以上面寫了 let doubled: Vec<i32>。

惰性的好處是中間步驟不會各自產生一個暫存陣列。filter 再 map 再 count，資料只被走過一次。

4. 重構 count_kinds

目前的 count_kinds 使用了三個可變變數搭配一個 for 迴圈來計算行數。 同樣的邏輯，我們也可以改用疊代器來實作。這兩種寫法在 Rust 中都很常見，讓我們先來看看它們的差異：

迴圈版本（目前的寫法）

只掃描資料一次，利用 match 將結果分派到三個對應的計數器中。

let mut empty_count = 0;
let mut comment_count = 0;
let mut code_count = 0;

for line in self.content.lines() {
    match Report::classify_line(line) {
        LineKind::Empty => empty_count += 1,
        LineKind::Comment => comment_count += 1,
        LineKind::Code => code_count += 1,
    }
}

(empty_count, comment_count, code_count)

疊代器版本

分別針對每種行別進行篩選與計算，語意上更具宣告性，且不需要使用可變變數。

let empty_count = self
    .content
    .lines()
    .filter(|line| matches!(Report::classify_line(line), LineKind::Empty))
    .count();

// comment_count 與 code_count 的寫法同理

(empty_count, comment_count, code_count)

請注意，這並不代表疊代器版本一定比較好。實際上，這個重構帶來了兩個明確的代價：

  • 資料必須被掃描三次：這三段疊代器鏈（chain）是各自獨立執行的，這意味著 classify_line 會被呼叫 3n 次，而非原本的 n 次。（疊代器的惰性只能確保「單一條鏈」內不產生多餘的中間集合，但無法將三條鏈自動合併為一次掃描。）
  • 失去編譯期的窮盡性檢查（Exhaustiveness Check）：這點比效能損失更為致命。如果未來 LineKind 新增了一個變體（例如 Doc），原本的迴圈版本會因為 match 沒有處理到新變體而直接編譯失敗，強迫你補上對應的邏輯。然而，疊代器版本卻能正常編譯，導致新的行別不會被算進任何一個計數器中，總行數也會因此對不上，且編譯器完全不會發出警告。

既然如此，為什麼還要這樣改呢？因為這個練習的主要目的是讓你在熟悉的程式碼中，練習使用 filter 與 count，而不是為了優化這段程式碼。 更重要的是，透過接下來的驗證步驟，你將體會到單元測試的價值：即使你大幅修改了核心邏輯的實作方式，測試也能確保程式的行為沒有被改壞，而不必單靠肉眼檢查。

💡 match 的窮盡性檢查是 Rust 最具價值的特性之一。在進行任何重構時，如果將「編譯期就能抓到的錯誤」變成了「執行期才會發現的錯誤」，即使程式碼看起來更簡潔，也必須停下來仔細評估是否值得。至於這次的重構划不划算，做完之後你可以自己體會看看。
小測驗一：let x = v.iter().map(|n| n * 2); 這一行執行後，發生了什麼？
小測驗二：.filter() 跟 .map() 對元素數量的影響是什麼？

換你動手

用疊代器重寫 count_kinds：
  1. 先執行一次 cargo test，確認四個測試都是 ok。這是你重構前的基準線。
  2. 把 count_kinds 裡的 for 迴圈與三個 mut 變數，換成三段 lines().filter(...).count()。
  3. 篩選條件用 matches!(Report::classify_line(line), LineKind::Empty) 這種寫法（跟你上一課測試裡用的一樣）。
  4. 再執行一次 cargo test，四個測試應該還是全部 ok。

驗證條件：cargo test 四個測試全過，cargo run -- notes.txt 印出的三個數字跟重構前一模一樣。這一課的重點不只是新語法——是你不用靠肉眼確認重構有沒有改壞東西，測試會告訴你。

💡 如果編譯器抱怨型別：lines() 給的是 &str，但 filter 的閉包收到的是參考的參考（&&str）。 classify_line(line) 通常會自動處理好；如果不行，試著寫 classify_line(*line)。把編譯器訊息貼給我，我可以幫你看。
這一課的成果
你第一次做了一個有測試護航的重構：改寫核心邏輯的實作，行為完全不變，而且是由 cargo test 幫你證明的，不是靠猜。同時你手上多了 filter / map / count / collect 這組工具——Rust 處理集合的日常寫法就是這些。
