run() / main() 分離、stderr 與離開碼

目標：將 main() 裡混雜的「讀檔邏輯」與「錯誤呈現方式」分離，使 load_report(filename) 也能使用 ? 運算子。同時，讓程式在發生錯誤時符合命令列工具的慣例：將錯誤訊息輸出至 stderr，並回傳非零的離開碼（exit code）。

讓我們先回顧目前的 main() 函式： 

fn main() {
    let args: Vec<String> = env::args().collect();

    let filename = match args.get(1) {
        Some(name) => name,
        None => {
            println!("用法：cargo run -- <檔名>");
            return;
        }
    };

    match load_report(filename) {
        Ok(mut report) => {
            report.add_title();
            println!("{}", report.summary());
            println!("{}", report.content);
            let (empty, comment, code) = report.count_kinds();
            println!("空行 {} 行，註解 {} 行，程式碼 {} 行", empty, comment, code);
        }
        Err(error) => println!("{}", error),
    }
}

在上一課（Lesson 17）中，我們學過這樣的樣板寫法：match load_report(filename) { Ok(...) => ..., Err(error) => println!("{}", error) }。也就是說，當結果為 Ok 時繼續執行後續動作，若為 Err 則將錯誤印出。這正是 ? 運算子想要簡化的情境。然而，如果我們直接在 main() 裡面寫 load_report(filename)?，編譯卻會失敗。

為什麼不能在 main() 裡直接使用 ?？

如同 Lesson 17 所提，? 運算子只能用在回傳型別為 Result（或 Option）的函式中。當 ? 遇到 Err(e) 時，它會提早結束並將 Err(e) 作為整個函式的回傳值送出。因此，只有當函式本身就宣告會回傳 Result 時，這個機制才能成立。

目前我們的 main() 並沒有標註回傳型別，這在 Rust 中代表它回傳的是 ()（即不回傳任何有意義的值）。如果在其中使用 load_report(filename)?，一旦發生錯誤，? 會試圖回傳 Err(e)，但這與 main() 預設回傳的 () 發生了衝突，導致編譯器拒絕編譯。

解法：將邏輯移至 run()，讓 main() 專職處理收尾

既然問題在於 main() 的回傳型別，解決方法很簡單：我們另外建立一個會回傳 Result 的函式（通常命名為 run()），並將原本 main() 的核心邏輯搬移過去。這樣一來，main() 就只需要負責一件事——呼叫 run()，並決定當錯誤發生時，該如何將訊息呈現給使用者。 

fn run() -> Result<(), AppError> {
    let args: Vec<String> = env::args().collect();

    let filename = match args.get(1) {
        Some(name) => name,
        None => {
            println!("用法：cargo run -- <檔名>");
            return Ok(());
        }
    };

    let mut report = load_report(filename)?;
    report.add_title();

    println!("{}", report.summary());
    println!("{}", report.content);

    let (empty, comment, code) = report.count_kinds();
    println!("空行 {} 行，註解 {} 行，程式碼 {} 行", empty, comment, code);

    Ok(())
}

fn main() {
    if let Err(error) = run() {
        eprintln!("{}", error);
        std::process::exit(1);
    }
}

現在的 run() 包含了原本 main() 的邏輯，主要有兩個不同之處：首先，它的回傳型別變成了 Result<(), AppError>；其次，因為 run() 確實回傳了 Result，所以我們現在可以合法地使用 load_report(filename)? 了。另外，如果使用者忘記提供檔名，程式印出用法說明後會執行 return Ok(());。這代表提早結束 run() 的執行，但因為這不算是一個系統錯誤，所以我們回傳 Ok(()) 表示正常結束。

main() 剩下的程式碼在做什麼？

現在的 main() 雖然只剩下短短幾行，但每一行都包含了新的概念。讓我們逐一拆解：

if let Err(error) = run() { ... } 其實是 match 語法的簡寫。如果寫成完整的 match，會長這樣： 

match run() {
    Ok(()) => {}
    Err(error) => {
        eprintln!("{}", error);
        std::process::exit(1);
    }
}

當我們只關心其中一種情況，而其他情況都不需要處理時，使用 match 會顯得多餘。這時就可以使用 if let PATTERN = EXPR { ... } 語法，它允許我們只針對特定的分支進行處理。以這裡為例：如果 run() 回傳 Ok(())，程式會直接略過大括號內的程式碼；只有當回傳 Err(error) 時，才會進入大括號，並將 error 變數綁定出來使用。與 match 必須窮舉所有可能性的規定不同，if let 允許我們忽略不在乎的變體，這正是它作為「簡寫」的優勢，非常適合用於「只在乎單一情況」的場景。

eprintln!("{}", error) 的用法與 println! 幾乎相同，唯一的差別在於開頭的 e。println! 會將訊息印到 stdout（標準輸出），而 eprintln! 則是印到 stderr（標準錯誤輸出）。這兩者是獨立的輸出管道，雖然終端機預設會將它們混合顯示，讓你感覺不出差異，但當使用者重新導向輸出時，差別就顯現出來了。例如，執行 cargo run -- notes.txt > out.txt 時，只有 stdout 的內容會被寫入 out.txt，而 stderr 的錯誤訊息仍會顯示在終端機畫面上。這樣就能有效地將正常結果與錯誤訊息分開。

std::process::exit(1) 會立刻終止整個程式，並將 1 作為離開碼（exit code）回報給呼叫此程式的環境（通常是 shell）。在命令列的慣例中，離開碼 0 代表執行成功，而任何非零的值都代表發生了錯誤。雖然一般使用者可能不會注意到離開碼，但對於將此程式寫入腳本自動化執行的人來說卻至關重要。Shell 可以透過 $? 取得上一個指令的離開碼，像是 if my_tool file.txt; then ... 這樣的條件判斷，也是依賴離開碼來運作的。如果程式發生錯誤卻依然回傳 0，呼叫它的腳本就會誤以為執行成功而繼續往下跑。

如果我們不呼叫 std::process::exit(1)，而是讓 main() 自然執行完畢，那麼即使我們剛剛才印出了錯誤訊息，程式的離開碼依然會是預設的 0。這正是我們在這一課必須修正的行為。

請注意實作的順序：必須先讓 run() 的回傳型別改為 Result，main() 才能使用 if let Err(...) 來接收錯誤。如果 run() 依然回傳 ()，那麼 main() 裡面的錯誤處理邏輯就毫無用武之地。因此，我們的步驟是：先解決「哪個函式應該回傳 Result」的問題，接著再來處理「main() 該如何呈現錯誤」。
小測驗一：為什麼要將邏輯移至 run()，而不是直接在 main() 裡使用 ?？
小測驗二：當 run() 執行成功並回傳 Ok(()) 時，main() 裡的 if let Err(error) = run() { ... } 大括號內會發生什麼事？
小測驗三：為什麼讀檔失敗時要呼叫 std::process::exit(1)，而不是印完錯誤訊息就讓程式自然結束？

換你動手

實作步驟：
  • 建立一個新函式 fn run() -> Result<(), AppError> { ... }，並將目前 main() 的內容整段搬移進去。接著，將 match load_report(filename) { Ok(mut report) => { ... } Err(error) => println!("{}", error) } 改寫為 let mut report = load_report(filename)?;，並保留後續的程式碼。在函式的最後補上 Ok(())。另外，在使用者未提供檔名的判斷分支中，將原本的 return; 改為 return Ok(());。
  • 將 main() 的內容替換為這三行程式碼：if let Err(error) = run() { eprintln!("{}", error); std::process::exit(1); }。

成功條件：執行 cargo build 時沒有編譯錯誤；執行 cargo run -- notes.txt 的輸出結果與改寫前一致。當讀取不存在的檔案時，錯誤訊息能正常印出，且透過 echo $? 檢查離開碼時，結果應為 1（改寫前因為 main() 沒有呼叫 process::exit，所以會是 0）；讀取空檔案時的行為也應相同。

這一課的成果
現在的 main() 職責非常明確，只負責「呼叫 run() 並決定如何呈現錯誤」，而實際的商業邏輯則全部封裝在回傳 Result 的 run() 函式中，這讓我們可以優雅地使用 ? 運算子。當程式發生錯誤時，錯誤訊息會被輸出至 stderr，且離開碼為 1——這完全符合命令列工具的標準行為，確保這支程式能安全地整合至腳本或管線（pipeline）中。速查表：run() / main() 分離參考卡。
