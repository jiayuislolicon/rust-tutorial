Lesson 0026 · Rust · CLI 工具養成路線

讓旗標帶一個值：--min 3

學習目標：把寫死在程式裡的 min 變成可以從命令列彈性輸入。過程中你會學到如何運用 while let 與 parse，並為 AppError 新增兩個錯誤變體。這是一堂 實作課 —— 我們要把前兩課（型別地圖、閉包）學到的心法，真正裝進你的 hello_cli 裡。

1. 你會卡在哪：門檻寫死在原始碼裡

上一課結束時，你的 main.rs 裡藏著這麼一行：

let min = 2;

這代表「只列出出現至少 2 次的單字」。但如果你今天想分析一份長篇報告，覺得 2 次太寬鬆，想改成 5 次呢？

目前的你只能這麼做：打開 main.rs、改掉數字、存檔、重新 cargo build、然後再跑一次。 如果想改回 2，還得把這套流程重來一遍。

這太不科學了！你要的應該是：cargo run -- --words --min 5 words.txt。不用改程式碼，也不用重新編譯。

然而，你目前的旗標迴圈還辦不到這件事。它現在只認得「開關型」的旗標 —— 看到 --count-only 就設為 true，沒看到就是 false。但 --min 的性質完全不同：它本身只是一個標籤， 真正的數值資訊，藏在它後面的那個參數裡。

2. 為什麼不能只多加一個 match 分支

你可能會想，那就依樣畫葫蘆，加個 match 分支不就好了？

"--min" => min = 2,   // 這行是錯的，等一下就會看到為什麼

先撇開這裡還是寫死 2 不談。真正的致命傷是：你並沒有把 --min 後面跟著的那個 5 給處理掉。當迴圈跑到下一圈時，它會抓到 "5"，因為它不是以 - 開頭， 就會掉進最後一個分支，被程式誤認為是「檔案名稱」。

實測這個版本，你會發現參數的順序居然會決定程式的生死：

指令 實際輸出
cargo run -- --words --min 2 words.txt 正常印出結果
cargo run -- --words words.txt --min 2 讀不到檔案：No such file or directory (os error 2)

為什麼會這樣？差別就在於「誰在後面」。 在第一種寫法裡，2 先被誤認為檔名存進了 filename， 但隨後出現的 words.txt 又把它覆蓋掉了，所以程式看起來安然無恙。但在第二種寫法裡，2 是最後一個參數， 它覆蓋了原本正確的 words.txt，於是程式傻傻地跑去找一個叫做 2 的檔案，最後當然會報錯。

💡 這種 Bug 其實比編譯錯誤更可怕。編譯錯誤會直接擋下你，但這種邏輯錯誤不會 —— 它會讓你的工具在某些參數順序下看似正常， 換個順序卻又突然崩潰。因此，正確地「把後面的值吃掉」絕對不是程式碼風格的問題，而是生死攸關的正確性問題。

3. for 迴圈不會把 iterator 交給你

既然關鍵在於要「吃掉下一個參數」，那我們就在迴圈裡手動多呼叫一次 next() 試試看： 

let mut args = env::args().skip(1);

for arg in args {
    if arg == "--min" {
        let value = args.next();   // 想再拿一個
        println!("{:?}", value);
    }
}

結果編譯器無情地拒絕了，並丟出 borrow of moved value: args： 

error[E0382]: borrow of moved value: `args`
  |
4 |     let mut args = env::args().skip(1);
  |         -------- move occurs because `args` has type `Skip<Args>`,
  |                  which does not implement the `Copy` trait
7 |     for arg in args {
  |                ---- `args` moved due to this implicit call to `.into_iter()`
9 |             let value = args.next();
  |                         ^^^^ value borrowed here after move
  |
  = note: a for loop advances the iterator for you, the result is stored in `arg`
help: if you want to call `next` on a iterator within the loop, consider using `while let`
  |
7 -     for arg in args {
7 +     while let Some(arg) = args.next() {

這段錯誤訊息非常豐富，裡面藏著三個獨立的情報，我們來逐一拆解：

  • a for loop advances the iterator for you：for 迴圈在底層其實就是默默地在幫你呼叫 next()，每一圈叫一次，然後把結果塞進 arg 裡。 它只是把這個動作封裝起來，不讓你看見。
  • args moved due to this implicit call to .into_iter()：這才是痛點！for 迴圈會直接把 iterator 的「所有權」整個端走（還記得 Lesson 10 的 move 嗎？）。所以一旦進了迴圈，args 就不再歸你管了，你當然不能在裡面對它呼叫 next()。
  • consider using while let：編譯器超貼心，直接把正確的語法跟改法都寫給你了。

總結來說，for 迴圈就像是自動導航，適合「你不需要自己控制節奏」的場景。但如果你需要在某些特定回合「手動多踩一腳油門」（多吃一個參數）， 你就必須把方向盤（iterator）緊緊握在自己手上。

4. while let：你已經會的語法

while let 看起來是個生面孔，但其實你在 Lesson 9 就已經學過它的雙胞胎兄弟了。我們來對照一下：

你已經會的 if let

解構一次。是 Some 就進去，不是就跳過。

if let Some(arg) = args.next() {
    // 用 arg
}

這一課的 while let

一直解構。每圈都叫一次 next()，直到配不上 Some 為止。 

while let Some(arg) = args.next() {
    // 用 arg
}

args.next() 回傳的是 Option<String>。當參數都被拿光時，它會回傳 None。這時 Some(arg) 這個模式（Pattern）就配對失敗了，迴圈便會優雅地結束。 在這裡，迴圈的結束條件不再是死板的計數器，而是「模式配對不上」。

最關鍵的差別在於：現在 args 的所有權還在你手上！因此，你完全可以在迴圈本體裡再呼叫一次 args.next()，主動吃掉下一個參數。而當迴圈進入下一圈時，就會自動從「再下一個」參數繼續開始。

5. 拿到的是 String，你要的是 usize

要記住一個大原則：命令列傳進來的參數，永遠都是文字。 所以 --min 5 給你的是 "5" 這個 String，而不是數字 5。要想比大小，我們得先把它轉成數字： 

let n: usize = value.parse()?;

但 parse 是有可能失敗的 —— 天知道使用者會不會手滑打成 --min abc。因此，它回傳的是 Result<usize, ParseIntError>，而不是單純的 usize。

既然看到了 Result，你的老朋友 ?（問號運算子，Lesson 17）就該上場了。但如果你直接加上去，編譯器又會擋下你： 

error[E0277]: `?` couldn't convert the error to `AppError`
   |
 9 | fn run() -> Result<(), AppError> {
   |             -------------------- expected `AppError` because of this
22 |                 Some(value) => min = value.parse()?,
   |                                            -------^ the trait `From<ParseIntError>`
   |                                                     is not implemented for `AppError`
   |
   = note: the question mark operation (`?`) implicitly performs a conversion
           on the error value using the `From` trait
help: the trait `From<ParseIntError>` is not implemented for `AppError`
      but trait `From<std::io::Error>` is implemented for it

這其實是 Lesson 17 那套錯誤處理機制的重播。? 在把錯誤往外丟之前，會試圖用 From 特徵（Trait）把它轉換成函式簽名上宣告的錯誤型別（也就是 AppError）。但目前 ParseIntError 還沒有通往 AppError 的橋樑，所以編譯器不知道該怎麼轉。

錯誤訊息的最後一行特別值得留意：but trait From<std::io::Error> is implemented for it。 編譯器在溫柔地提醒你：「嘿，你之前為了 fs::read_to_string 已經寫過一個類似的轉換橋樑囉！」 我們只要照著那個形狀，再搭一座橋就好了。

6. 兩種失敗，兩個變體

針對 --min 這個旗標，使用者可能會犯兩種不同的錯。這兩種錯值得我們分開處理，因為我們需要給出不同的錯誤提示：

使用者打了什麼 哪裡出問題 新變體
--min abc 值拿得到，但不是數字 BadNumber(ParseIntError)
--words words.txt --min --min 是最後一個參數，根本沒有值 MissingValue(String)

第二種錯誤（少給數字），從型別上就能一眼看穿：因為 args.next() 回傳的是 Option，而 None 就是你必須面對的分支。在 Rust 裡，你絕對不會忘記處理它，因為 match 的「窮盡性檢查（Exhaustiveness Check）」會死死盯著你，不准你漏掉任何一種可能。

7. 完整的改動

在 errors.rs 加兩個變體、兩個 Display 分支、一個 From： 

pub enum AppError {
    ReadFailed(std::io::Error),
    Empty,
    UnknownFlag(String),
    MissingValue(String),
    BadNumber(std::num::ParseIntError),
}
            AppError::MissingValue(flag) => write!(f, "{} 後面少了一個數字", flag),
            AppError::BadNumber(e) => write!(f, "數字格式錯誤：{}", e),
impl From<std::num::ParseIntError> for AppError {
    fn from(e: std::num::ParseIntError) -> AppError {
        AppError::BadNumber(e)
    }
}

main.rs 的旗標迴圈：

🔴 重構前

for 拿走了 iterator，你沒有辦法在迴圈裡多走一步。

for arg in env::args().skip(1) {
    match arg.as_str() {
        "--count-only" => count_only = true,
        "--words" => words_count_only = true,
        _ if arg.starts_with("-") => return Err(AppError::UnknownFlag(arg)),
        _ => filename = Some(arg),
    }
}

🟢 重構後

iterator 在 args 手上，--min 分支可以自己再吃一個參數。 

let mut min: usize = 1;

let mut args = env::args().skip(1);

while let Some(arg) = args.next() {
    match arg.as_str() {
        "--count-only" => count_only = true,
        "--words" => words_count_only = true,
        "--min" => match args.next() {
            Some(value) => min = value.parse()?,
            None => return Err(AppError::MissingValue("--min".to_string())),
        },
        _ if arg.starts_with("-") => return Err(AppError::UnknownFlag(arg)),
        _ => filename = Some(arg),
    }
}

最後，別忘了把 --words 區塊裡原本寫死的 let min = 2; 刪掉。現在這個門檻值已經交由迴圈來動態設定了。

💡 為什麼預設值要改成 1，而不是 2？ 因為 min = 1 代表「不過濾」（只要出現過的字，至少都會出現 1 次）。 當使用者沒有特別指定 --min 時，顯示全部結果，這才是比較符合直覺的預設行為。
💡 關於 let mut min: usize = 1; 的小秘密： 其實 : usize 這個型別標註是可以省略的。 因為在後面的程式碼中，我們寫了 *pair.1 >= min，拿它跟 &usize 去比大小，這時它的型別就已經被編譯器「釘死」了。 寫出來只是為了體貼讀程式碼的人 —— 變數宣告和函式簽名，永遠是人類確認型別最快的地方。

8. 回頭看看上一課的閉包

在 --words 區塊中，有一行程式碼我們連碰都沒碰，但它的意義卻已經昇華了： 

pairs.retain(|pair| *pair.1 >= min);

在以前，min 是寫死的 2，編譯器在編譯時就對它瞭若指掌。但現在，它是使用者在命令列上臨時輸入的數字， 在編譯階段，這個數字根本還不存在！

這完美呼應了 Lesson 25 中那個 can't capture dynamic environment in a fn item 的錯誤。一般的 fn 函式就像密室，看不到外面的變數，所以它根本無從得知 min 到底是多少。 但閉包可以，因為它把 min 裝進百寶袋，一起帶著走了。

在上一課，這可能只是編譯器的一句囉嗦限制；但在這一課，它卻成為了你的工具「能不能動態接受使用者輸入」的關鍵分水嶺。

9. 練習一：把三種失敗都跑一次

照著第 7 節做完改動後，請把下面每一行指令都跑過一次，確認輸出跟表格一致。

指令 預期輸出
cargo run -- --words words.txt apple: 3 / banana: 2 / cherry: 1
cargo run -- --words --min 2 words.txt apple: 3 / banana: 2
cargo run -- --min 3 --words words.txt apple: 3
cargo run -- --words --min abc words.txt 數字格式錯誤：invalid digit found in string
cargo run -- --words words.txt --min --min 後面少了一個數字
cargo test 5 個測試全過，一個字都不用改
💡 第 3 行是重點。--min 3 放在 --words 前面也能正常運作，因為值被 args.next() 吃掉了，不會漏到檔名那一格。 這正是第 2 節那個 bug 被修好的最佳證據。

10. 練習二：讓編譯器再示範一次窮盡性

這一題不用寫新功能，只是要驗證一個你已經聽過、但可能還沒親眼看過的規則。

  1. 在 errors.rs 的 AppError 裡再加一個變體，例如 TooManyFiles。先不要動 Display。
  2. cargo build。預測一下：會過嗎？
  3. 讀編譯器的訊息。它會說 non-exhaustive patterns，並且精準指出是哪一個變體沒被涵蓋到。
  4. 把這個變體刪掉，回到原本的狀態。

重點不是這個變體本身，而是這件事：enum 只要加了一個變體，所有沒處理它的 match 都會直接編譯失敗。如果你在 TypeScript 裡加一個 union 成員，只有開了嚴格設定、而且回傳型別剛好夠窄的地方才會被抓到。 但在 Rust 裡，這是語言層面給你的鐵壁保證。
