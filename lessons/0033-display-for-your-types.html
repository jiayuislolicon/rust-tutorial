Lesson 0033 · Rust · CLI 工具養成路線

Display — 讓型別自己決定怎麼印出來

學習目標：在 main.rs 裡，你為了把三個數字塞進 println!，不得不把 LineStats 拆解成三個變數。這一課你會為 LineStats 實作 Display trait，讓 struct 自己決定輸出格式，然後把呼叫端簡化成一行 println!("{}", stats)。

1. 拆解 struct 只是為了印出來

打開 hello_cli/src/main.rs，在 run() 底部找到這幾行： 

let LineStats {
    empty,
    comment,
    code,
} = report.line_stats();
println!("空行 {} 行，註解 {} 行，程式碼 {} 行", empty, comment, code);

你從 LineStats 裡拆出三個欄位，立刻又把它們塞進 format string。struct 本來就握有這三個值——你只是把它已經知道的東西重新打包一遍。

這個問題你以前就遇過。Lesson 16 裡，AppError 沒辦法用 println!("{}", err) 印出來。解法是實作 Display：你寫了 impl fmt::Display for AppError，告訴編譯器每個 variant 該產生什麼文字，之後 {} 就能直接用了。

LineStats 面對的是同一個問題。替它加上 Display 實作，上面那六行就能縮成一行。

2. 為 LineStats 實作 Display

打開 hello_cli/src/report.rs。把下面這段加在現有的 impl Report 外面——這是 impl Display for LineStats，不是 Report 的方法： 

use std::fmt;

impl fmt::Display for LineStats {
    fn fmt(&self, f: &mut fmt::Formatter) -> fmt::Result {
        write!(
            f,
            "空行 {} 行，註解 {} 行，程式碼 {} 行",
            self.empty, self.comment, self.code
        )
    }
}

這個簽名的每一部分都是 Display trait 規定的——你不能改函式名稱、參數或回傳型別。你能控制的是函式本體：write! 那行決定了 {} 最後會印出什麼文字。

format!(...) 會把格式化後的內容組成一個 String 回傳給你；write!(f, ...) 則會把格式化後的內容寫進 Display::fmt() 收到的 formatter f。這裡的 f 是 Rust 的格式化系統提供的輸出目標，你只需要負責把 LineStats 想顯示的內容寫進去。

3. 簡化 main.rs

🔴 修改前 —— 拆解 struct，手動組 format string
let LineStats {
    empty,
    comment,
    code,
} = report.line_stats();
println!("空行 {} 行，註解 {} 行，程式碼 {} 行", empty, comment, code);
🟢 修改後 —— 讓型別自己格式化
println!("{}", report.line_stats());

一行取代六行。format string 現在住在 LineStats 裡，緊挨著它的資料。如果你之後加了一個欄位——比如 doc_comment——只要改 Display 的 impl 一次，整份程式裡每一個 println!("{}", stats) 都會自動跟上。用舊寫法的話，你得找出每一處拆解 struct 的地方，逐一修改。

改完之後，main.rs 也不再需要 use crate::report::LineStats; 這行了。刪掉那行 import，跑 cargo build 確認一切能編譯。

4. Debug vs Display：兩種讀者

LineStats 現在有兩個格式化 trait：Debug（來自 #[derive(Debug)]）和 Display（來自你剛寫的 impl）。它們服務的對象不同：

Debug ({:?}) Display ({})
對象 你，寫程式的人 終端使用者
怎麼取得 #[derive(Debug)] 手寫 impl fmt::Display
LineStats 的輸出 LineStats { empty: 1, comment: 2, code: 7 } 空行 1 行，註解 2 行，程式碼 7 行

Debug 可以 derive，因為它的規則是機械式的：印出型別名稱，再印出每個欄位名稱和值。不需要人類做判斷。Display 不能 derive，因為要印什麼文字是一個設計選擇——只有你知道該說 "empty: 1" 還是「空行 1 行」。

測試和除錯時用 {:?}。使用者會看到的輸出用 {}。一個型別可以同時擁有兩者。

5. 你會一再重用的模式

到目前為止，你在這個專案裡寫了兩次 impl fmt::Display：一次給 AppError（Lesson 16），一次給 LineStats（這一課）。形狀永遠一樣： 

impl fmt::Display for YourType {
    fn fmt(&self, f: &mut fmt::Formatter) -> fmt::Result {
        write!(f, "...", self.field_a, self.field_b)
    }
}
  • 簽名——fn fmt(&self, f: &mut fmt::Formatter) -> fmt::Result——是固定的。你不能改名，也不能改參數型別。
  • 函式本體——write! 那行——是你的。對 enum 來說，你 match self，為每個 variant 產生不同文字（像 AppError）。對 struct 來說，你讀 self.field，組出一則訊息（像 LineStats）。

每當你發現自己為了把值塞進 println! 而拆解 struct 或 match enum，那就是型別該實作 Display 的訊號。

你為 LineStats 實作了 Display，把六行拆解再印出的程式碼縮成一行 println!("{}", stats)。你也看清了 Debug（derive 出來，給寫程式的人看）和 Display（手寫，給使用者看）的差別。這個模式——impl fmt::Display for YourType 加上 write!(f, ...) 本體——每次形狀都一樣，struct 和 enum 都適用。

你的專案現在有兩個 Display 實作：AppError（Lesson 16）和 LineStats（這一課）。下次再發現自己拆解 struct 只是為了印出來，你就知道該做什麼了。
