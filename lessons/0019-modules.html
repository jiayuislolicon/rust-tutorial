Lesson 0019 · Rust · CLI 工具養成路線

用 mod 拆成多檔案

學習目標：將原本全部塞在 main.rs 裡的錯誤型別與 Report 邏輯，依職責拆分到三個不同的檔案中。同時，學會 Rust 模組系統中最關鍵的三個字：mod、pub 與 use。

🔴 重構前：所有程式碼擠在 main.rs

目前 AppError、Report、run 與 main 全部都寫在同一個檔案裡。隨著檔案越來越長，尋找特定邏輯會變得越來越花時間。下方的程式碼用 ... 省略了具體實作，僅用來示意目前的檔案結構： 

// main.rs（121 行，全部東西都在這，示意用，非可執行程式碼）
enum AppError { ... }
impl fmt::Display for AppError { ... }
impl From<std::io::Error> for AppError { ... }

struct Report { ... }
enum LineKind { ... }
impl Report { ... }

fn load_report(...) -> Result<Report, AppError> { ... }
fn run() -> Result<(), AppError> { ... }
fn main() { ... }

🟢 重構後：依職責拆分成三個檔案

將錯誤型別、報表邏輯與程式進入點，各自獨立成專屬的檔案：

src/
├── main.rs      // mod 宣告 + run() + main()
├── errors.rs    // AppError + Display + From
└── report.rs    // Report + LineKind + load_report

1. 為什麼需要拆分檔案？

目前的 main.rs 大約只有 120 行，閱讀起來還算輕鬆。但隨著專案發展，我們一定會繼續加入新功能。如果未來要多支援一種檔案格式，或是新增不同的錯誤型別，這個檔案只會越滾越大，變得難以維護。

拆分檔案的好處非常直接：找東西變快了。想修改錯誤訊息時，直接打開 errors.rs；想調整報表邏輯時，直接打開 report.rs。你再也不需要在一個冗長的檔案裡來回滾動捲軸了。

💡 對照 TypeScript：在 TypeScript 專案中，你本來就會將 errors.ts 與 report.ts 拆成不同的檔案，透過 export 將需要公開的部分匯出，再用 import { Report } from './report' 將其引入使用。在 Rust 裡，pub 就相當於 export，而 use 則相當於 import。兩者的核心概念完全相同，只是使用的關鍵字不一樣而已。

2. mod：告訴編譯器「這裡有其他的檔案」

與某些語言不同，Rust 不會自動將資料夾裡所有的 .rs 檔案都納入編譯。你必須在專案的進入點（也就是 main.rs）中明確地宣告它們： 

mod errors;
mod report;

這兩行程式碼的意思是：「請去找 src/errors.rs 與 src/report.rs 這兩個檔案，並將它們當作模組編譯進目前的專案中」。如果漏寫了這兩行，即使檔案確實存在於資料夾中，編譯器也會視若無睹。

3. pub：預設所有內容都是私有的 (Private)

Rust 的存取規則與 TypeScript 恰好相反：TypeScript 預設整個檔案的內容都可以被 import（只要你有 export）；而 Rust 預設整個模組內的內容都是私有的，除非你明確加上 pub（public 的縮寫）。

沒有加上 pub 的型別或函式，就只能在它所在的檔案（也就是同一個模組）內部使用。如果 main.rs 想要使用 report.rs 裡的 Report 結構體，我們就必須在 report.rs 中加上適當的 pub 關鍵字。以下方程式碼為例（用 ... 省略了未變動的實作細節，僅標示需要加上 pub 的地方）： 

pub struct Report {
    filename: String,   // 欄位不加 pub 也沒關係，
    content: String,    // 因為外部只透過下面的 pub 方法存取
    line_count: usize,
}

impl Report {
    pub fn new(filename: &str, content: String) -> Report { ... }
    pub fn summary(&self) -> String { ... }
    pub fn add_title(&mut self) { ... }
    pub fn count_kinds(&self) -> (usize, usize, usize) { ... }
}

pub fn load_report(filename: &str) -> Result<Report, AppError> { ... }
  • pub struct Report：為了讓 main.rs 能夠看見並使用這個型別，結構體本身必須加上 pub。
  • 欄位不需要 pub：因為 main.rs 只會透過呼叫 report.summary() 等方法來操作資料，並不會直接存取 report.filename，所以欄位保持私有即可正常運作。
  • 每個需要被外部呼叫的方法都要加上 pub：只要漏掉一個，當外部嘗試呼叫該方法時，編譯器就會無情地報錯。
  • LineKind 不需要 pub：這個列舉（enum）只在 report.rs 內部的 count_kinds 方法中使用，main.rs 完全不需要知道它的存在，因此維持私有即可。

4. use：將路徑引入目前的作用域

在宣告了 mod report; 之後，Report 結構體的完整路徑會變成 report::Report（如果從專案根目錄算起，則是 crate::report::Report）。每次使用都要寫這麼長的全名實在太囉唆了，這時 use 就能派上用場。它能幫我們將特定路徑「引入」目前的作用域，讓我們可以直接使用簡短的名稱： 

mod errors;
mod report;

use errors::AppError;
use report::{Report, load_report};

fn run() -> Result<(), AppError> {
    let mut report = load_report(filename)?;   // 不用寫 report::load_report
    ...
}

5. errors.rs 裡的小細節：實作 Trait 時不需要加 pub

當我們寫下 impl From<std::io::Error> for AppError 時，這段實作本身不需要額外加上 pub。因為 impl 區塊並不是獨立的型別或函式，Rust 不會限制它的存取。只要 AppError 這個型別本身是公開的（pub），當我們在 report.rs 裡使用 ? 運算子時，Rust 就能自動找到並執行這個型別轉換。

小測驗一：如果在 report.rs 裡有一個沒加 pub 的函式，而 main.rs 嘗試呼叫它，會發生什麼事？
小測驗二：如果 main.rs 裡忘記寫 mod report; 這一行，但 src/report.rs 檔案確實存在於資料夾中。編譯的結果會是？

換你動手

實作三步驟：
  1. 新增 src/errors.rs 檔案。將 AppError、它的 Display 實作，以及 From<std::io::Error> 的實作整段搬移過去。記得在 enum AppError 前面加上 pub。
  2. 新增 src/report.rs 檔案。將 Report、LineKind 以及 load_report 函式整段搬移過去。 接著，為 struct Report、impl Report 裡面的每個方法，以及 load_report 都加上 pub（LineKind 及其欄位則不需要）。 最後，在 report.rs 的開頭加上 use crate::errors::AppError;，這樣檔案裡才能順利使用 AppError。
  3. 回到 main.rs，刪除已經搬走的程式碼，只留下 run() 和 main()。並在檔案的最開頭加上以下宣告與引入： 
    mod errors;
mod report;

use errors::AppError;
use report::load_report;

驗證條件：執行 cargo build 時沒有任何編譯錯誤。接著執行 cargo run -- notes.txt，測試正常檔案、不存在的檔案以及空檔案，確認程式的行為與 Lesson 18 完全一致。

這一課的成果
我們成功將原本 120 多行的單一檔案，重構為三個各司其職的模組：errors.rs 專管錯誤處理，report.rs 負責資料與邏輯，而 main.rs 則單純作為程式的進入點。

本課學到的三個關鍵字：mod（宣告模組）、pub（開放存取權限）、use（引入路徑），是往後你在開發任何 Rust 專案時都會用到的核心基礎。速查表：mod / pub / use 參考卡。
