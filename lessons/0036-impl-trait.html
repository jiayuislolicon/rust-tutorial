impl Trait — 把「具體型別」藏起來

學習目標： 這一課先不要急著背 impl Iterator。 真正要理解的是：Rust 有時候「知道函式回傳的具體型別」，只是那個型別實在太複雜、甚至包含匿名的 closure， 我們根本不想也無法在函式簽名上把它寫出來。 impl Trait 就是用來告訴 Rust： 「我不寫出具體型別的名字，但這個值一定實作某個 trait。」

1. 先回答：為什麼需要 impl Trait？

先看一個我們已經很熟悉的函式：

fn get_name() -> String {
    String::from("Alice")
}

這裡完全沒有問題，因為我們知道回傳值就是 String， 而且 String 這個型別名稱很好寫。

但 Rust 的 iterator 很容易遇到另一種情況。 例如我們想要「找出所有包含關鍵字的行」： 

self.content
    .lines()
    .filter(move |line| line.to_lowercase().contains(&owned))

這個東西不是 Vec<&str>。 它是一個 iterator，而且 filter() 會產生一個新的 iterator。 更麻煩的是，filter() 裡面的 closure 也有 Rust 自己產生的匿名型別。

所以它實際上會長得非常像：

Filter<
    Lines<'_>,
    某個 Rust 自動產生的 closure 型別
>
這裡才是問題，不是「Rust 不知道它是什麼」。 恰恰相反：Rust 非常知道它是什麼，只是我們不需要知道那個完整名字。

2. 這時候 impl Trait 做了什麼？

我們可以把函式寫成：

pub fn matching_lines(
    &self,
    pattern: &str
) -> impl Iterator<Item = &str> {
    let owned = pattern.to_lowercase();

    self.content
        .lines()
        .filter(move |line| line.to_lowercase().contains(&owned))
}

注意這裡有兩個很重要的觀念：

  1. 具體型別仍然存在， impl Trait 並沒有把型別變成「不知道」。
  2. 只是把具體型別的名字藏起來， 編譯器仍然知道真正的型別，也可以用它進行靜態派發。

3. 為什麼不直接寫 Iterator？

可能會想：「既然我只在乎它是一個 Iterator，為什麼不直接寫？」

// 這不是我們想要的寫法
fn matching_lines(&self, pattern: &str) -> Iterator<Item = &str>

因為 Iterator 是 trait，不是一個可以直接拿來當一般回傳值的具體型別。 Rust 需要知道回傳值的實際型別大小與結構。

impl Iterator 的意思不是「回傳一個叫 Iterator 的東西」， 而是： 

「回傳某一個型別」
        ↓
「這個型別實作 Iterator」
        ↓
「但我不想在 API 上寫出它的完整名字」

4. 那為什麼不用 Box<dyn Iterator>？

這正好可以和上一課的 Box<dyn Formatter> 接起來。 兩種寫法都可以把「具體型別」藏在 API 背後，但它們藏型別的方式不同。

impl Trait：具體型別早就確定了

fn matching_lines(...) -> impl Iterator<Item = &str>

函式本身決定了回傳哪一個具體型別，使用者只是不用知道那個型別的名字，仍然是靜態派發。

dyn Trait：允許透過 trait object 使用不同具體型別

fn make_formatter(...) -> Box<dyn Formatter>

這種情況下，程式可以在執行時根據條件選擇不同的 Formatter 實作。 呼叫端只需要透過 trait object 使用它。

所以最重要的差別不是「有沒有把型別藏起來」。 兩者都能藏，真正的差別是：你需不需要讓同一個 API 在執行時承載不同的具體型別。

impl Trait dyn Trait
具體型別 編譯期已確定，而且每次都對應同一種具體型別 可以透過 trait object 使用不同的具體型別
派發 靜態派發 動態派發
主要用途 型別很複雜、匿名，但不需要動態選擇 需要在執行時處理不同實作
Box 不需要因為 impl Trait 本身而使用 Box 常見寫法是 Box<dyn Trait>，但 dyn Trait 本身不等於 heap
  • impl Trait 是「我知道是哪一型，只是不想寫名字」。
  • dyn Trait 是「我只需要透過這個 trait 使用它，而且可以容納不同的具體實作」。

5. 回到我們的 --grep

現在就可以理解為什麼 matching_lines() 很適合使用 impl Iterator。 

pub fn matching_lines(
    &self,
    pattern: &str
) -> impl Iterator<Item = &str> {
    let owned = pattern.to_lowercase();

    self.content
        .lines()
        .filter(move |line| line.to_lowercase().contains(&owned))
}

不管使用者輸入的是：

--grep "fn"
--grep "error"
--grep "hello"

matching_lines() 裡面的 iterator chain 都是同一種結構。 使用者輸入的字串會改變「哪些行符合」，但不會改變回傳值的具體型別。

因此這裡完全沒有必要使用 dyn Iterator。 我們只是懶得、也無法寫出那個 iterator chain 的完整型別名稱。

6. impl Iterator 還有另一個好處：保留惰性

iterator 本身是惰性的，matching_lines() 回傳的是一個 Iterator，不代表它已經把所有符合 "fn" 的行找出來了： 

let lines = report.matching_lines("fn");

真正要求下一個元素時，iterator 才會逐步往前走：

for line in lines {
    println!("{}", line);
}

因此我們不需要為了「讓回傳型別比較好寫」而把結果先收集成 Vec： 

// 可以，但會立刻收集所有結果
fn matching_lines(...) -> Vec<&str>

impl Iterator 讓我們可以直接把 iterator chain 傳出去， 由呼叫端決定什麼時候把結果算好。

7. 使用 matching_lines()

參數解析先加入 --grep：

"--grep" => match args.next() {
    Some(value) => grep = Some(value),
    None => return Err(AppError::MissingValue("--grep".to_string())),
},

接著在 main 裡：

if let Some(ref pattern) = grep {
    for line in report.matching_lines(pattern) {
        println!("{}", line);
    }

    return Ok(());
}
  1. matching_lines() 回傳一個可以逐行取資料的 Iterator
  2. for 迴圈逐個取得
  3. println!

8. impl Trait 不代表「可以回傳任何實作」

這是這一課最容易搞錯的地方。

看到：

fn foo() -> impl Display

不要把它理解成：

「foo 可以隨便回傳任何有實作 Display 的型別。」

更準確的理解是：「foo 會回傳某一個固定的具體型別， 而這個型別實作 Display。 我不需要知道它的名字。」

所以這樣不能編譯：

fn pick(flag: bool) -> impl std::fmt::Display {
    if flag {
        "hello"    // &str
    } else {
        42         // i32
    }
}

因為兩個分支是不同的具體型別： &str 與 i32。 即使它們都實作 Display， impl Trait 仍然要求函式的回傳型別能被視為同一個具體型別。

9. 那什麼時候才需要 dyn Trait？

如果你的需求真的是：

if 某個條件 {
    使用 FormatterA
} else {
    使用 FormatterB
}

而且這兩個 formatter 是不同的具體型別， 那麼你就需要一種方式讓它們透過共同的 trait 介面被使用。 這就是上一課 Box<dyn Formatter> 的用途。

所以可以用一個很實用的判斷方式：

  1. 只是型別太醜、太長、包含 closure / iterator chain？ → impl Trait
  2. 真的需要在執行時選擇不同的實作？ → 考慮 dyn Trait
  3. 我根本知道具體型別，而且型別名稱很好寫？ → 直接寫具體型別

10. 參數位置的 impl Trait

impl Trait 不只可以出現在回傳位置，也可以寫在函式參數： 

fn print_all(items: impl Iterator<Item = String>) {
    for item in items {
        println!("{}", item);
    }
}

這裡的意思是： 「呼叫者可以傳入任何實作 Iterator<Item = String> 的型別。」

它和泛型的概念很接近。例如：

fn print_all<I>(items: I)
where
    I: Iterator<Item = String>,
{
    for item in items {
        println!("{}", item);
    }
}

這一部分先記住「參數位置的 impl Trait 是一種比較精簡的泛型寫法」即可。 當你需要在多個地方精確引用同一個型別參數時，再使用完整的泛型語法會比較清楚。

11. 這一課真正要記住什麼？

impl Trait 的核心不是「Iterator」。

Iterator 只是非常常見的使用情境，因為 iterator chain 的具體型別通常又長又包含匿名 closure。

真正的概念是：
「具體型別已經確定，只是我不想／不能在 API 上寫出它的名字。」

因此看到：

-> impl Iterator<Item = &str>

腦中可以直接翻譯成：「回傳某個固定的 Iterator。 Rust 知道它真正是誰。 我只需要知道它可以當 Iterator 使用。

這樣再回頭看上一課與這一課，就會形成一個很清楚的對比：

impl Trait
    ↓
「型別固定，只是不想寫名字」
    ↓
靜態派發

dyn Trait
    ↓
「透過共同介面使用不同具體型別」
    ↓
動態派發

這一課的成果
你現在不需要把 impl Trait 背成一個「Iterator 專用語法」。

看到它時，先翻譯成： 「某個具體型別已經確定，只是把它的名字藏起來。」

iterator chain 是最常見的例子，因為 closure 會讓具體型別非常難以手寫。 而上一課的 dyn Trait 則是在另一種情況下出場： 你需要透過共同 trait 介面處理不同的具體實作。
