Lesson 0035 · Rust · CLI 工具養成路線

Trait Object — 在執行時才決定呼叫誰

學習目標：你的工具目前只會用固定格式印報告。使用者想要 --format json，你也想加這個功能。問題在於：要用哪種格式，要到 執行時才知道——沒辦法在寫程式時就寫死在型別裡。這一課你會用 trait object（Box<dyn Trait>），讓程式依使用者的選擇，在執行時呼叫正確的實作。

1. 泛型做不到的事

寫一個函式 fn print_it<T: Display>(val: T)，編譯器會為每個用到的 T 各產生一份專屬的機器碼——這叫靜態派發（static dispatch）。呼叫時直接跳到正確的函式，不需要查表，所以很快。

但你的 --format 旗標是在 parse 命令列之後才決定要用 plain 還是 json。在 parse 完成之前，你根本不知道該用哪種 formatter。你可能會想寫： 

fn pick_formatter(name: &str) -> ??? {
    match name {
        "plain" => PlainFormatter,
        "json"  => JsonFormatter,
        _ => panic!(),
    }
}

回傳型別填什麼？PlainFormatter 和 JsonFormatter 是兩個不同的 struct——大小、layout 都不一樣，沒辦法塞進同一個回傳型別的位置。泛型在編譯期就要確定型別；但這裡的選擇，要等到 使用者跑程式的那一刻才知道。

2. Trait Object：把型別藏進 Box

解法是 trait object。你不再告訴編譯器具體是哪個型別，而是說：「我不知道是誰，但它一定實作了某個 trait。」寫法是 Box<dyn Formatter>，拆開來看：

  • dyn Formatter — 「某個實作了 Formatter 的型別，但我現在不說是誰」
  • Box<...> — 把它放到 heap 上。編譯器不知道具體型別的大小，沒辦法在 stack 上分配固定空間

呼叫方法時，程式會先查一張小表（vtable），找到正確的函式指標，再跳過去——這叫 動態派發（dynamic dispatch）。比起靜態派發多了一次間接跳轉，但在 CLI 工具這個層級，差異完全可以忽略。

3. 定義 Formatter trait

新建 hello_cli/src/formatter.rs，定義一個 trait 和兩種實作： 

use crate::report::Report;

pub trait Formatter {
    fn format_report(&self, report: &Report) -> String;
}

pub struct PlainFormatter;

impl Formatter for PlainFormatter {
    fn format_report(&self, report: &Report) -> String {
        let stats = report.line_stats();
        format!(
            "{}\n{}\n{}",
            report.summary(),
            report.content,
            stats
        )
    }
}

pub struct JsonFormatter;

impl Formatter for JsonFormatter {
    fn format_report(&self, report: &Report) -> String {
        let stats = report.line_stats();
        format!(
            "{{
  \"filename\": \"{}\",
  \"lines\": {},
  \"empty\": {},
  \"comment\": {},
  \"code\": {}
}}",
            report.filename,
            report.line_count(),
            stats.empty,
            stats.comment,
            stats.code,
        )
    }
}

兩個 struct 都是零大小型別（zero-sized type, ZST）——它們不存任何資料，只是用來掛 impl Formatter。這裡它們大小相同只是巧合；對 trait object 來說，背後的 struct 就算大小不同也沒關係。

4. 工廠函式回傳 Box<dyn Formatter>

trait 和實作都就位了，接下來寫一個函式，依使用者選的格式回傳對應的 formatter： 

pub fn make_formatter(format: &str) -> Option<Box<dyn Formatter>> {
    match format {
        "plain" => Some(Box::new(PlainFormatter)),
        "json"  => Some(Box::new(JsonFormatter)),
        _       => None,
    }
}

Box::new(PlainFormatter) 做了兩件事：把 PlainFormatter（一個具體型別）放到 heap 上，再附上 vtable 指標——合起來就是一個 trait object。回傳出去之後，呼叫端只知道「這東西會 format_report()」，不需要也不應該知道底層是哪個 struct。

5. 在 main 裡使用

最後把這一切接到 main.rs。先加入 --format 的解析，再呼叫 make_formatter()： 

"--format" => match args.next() {
    Some(value) => format = value,
    None => return Err(AppError::MissingValue("--format".to_string())),
},

使用時：

let formatter = make_formatter(&format)
    .ok_or_else(|| AppError::UnknownFlag(format!("--format {}", format)))?;

println!("{}", formatter.format_report(&report));

這裡有一個小環節值得拆開看。make_formatter() 回傳的是 Option<Box<dyn Formatter>>：如果使用者輸入的是我們支援的格式，就會得到 Some(formatter)；如果格式不認識，就會得到 None。

但 run() 需要回傳的是 Result。所以當 make_formatter() 得到 None 時，我們不能直接用 ? 返回，必須先把這個 None 轉成一個具體的錯誤，例如 AppError。

.ok_or_else(|| ...) 就是在做這個轉換：

Some(formatter)  →  Ok(formatter)
None             →  Err(AppError)

轉換成 Result 之後，就可以使用 ?： 如果是 Ok，繼續往下執行；如果是 Err，就提早從 run() 返回錯誤。

所以這段：

let formatter = make_formatter(&format)
    .ok_or_else(|| AppError::UnknownFlag(format!("--format {}", format)))?;

可以把它讀成：「取得 formatter；如果找不到，就把 None 變成這個 AppError，然後交給 ? 處理。」

formatter 的型別是 Option<Box<dyn Formatter>>。當你呼叫 .format_report() 時，Rust 會在執行時透過 vtable 找到實際型別對應的實作並呼叫它。對你來說，寫法和呼叫一般方法一樣；差別只在於 Rust 是在執行時才決定實際要呼叫哪個實作。

6. 試跑一下

$ cargo run -- hello_cli/src/main.rs
main.rs：共 70 行
...
空行 4 行，註解 0 行，程式碼 66 行

$ cargo run -- --format json hello_cli/src/main.rs
{
  "filename": "hello_cli/src/main.rs",
  "lines": 70,
  "empty": 4,
  "comment": 0,
  "code": 66
}

同一行 formatter.format_report()，使用者選 plain 就走 plain 的路，選 json 就走 json 的路——動態派發就是在做這件事。

7. 泛型 vs trait object：何時用哪個

泛型和 trait object 都可以讓我們使用「實作了某個 trait 的型別」，但最大的差別在於： Rust 什麼時候知道這個具體型別是誰？

如果在編譯程式時就知道具體型別，可以使用泛型：

fn print_report<F: Formatter>(formatter: F, report: &Report) { println!("{}", formatter.format_report(report)); } print_report(PlainFormatter, &report);

這裡呼叫 print_report() 時，Rust 已經知道 F 是 PlainFormatter。 如果另一個地方傳入 JsonFormatter，Rust 也知道那一次的 F 是 JsonFormatter。 因此編譯器可以在編譯期決定要呼叫哪個實作——這就是 靜態派發（static dispatch）。

但 --format 的情況不一樣。程式編譯時，我們不知道使用者最後會輸入 plain 還是 json。必須等程式啟動、解析完命令列參數後， 才能決定要建立哪一個 formatter。 

程式編譯
  ↓ 
程式啟動
  ↓ 
讀取 --format
  ↓
使用者輸入 "json"
  ↓
現在才知道要用 JsonFormatter

這時候就適合使用 trait object：

Box<dyn Formatter>

它代表：「我現在不知道具體是哪個 formatter，但我知道它一定實作了 Formatter。」 等到程式執行時選出具體的 formatter 後，Rust 再透過 vtable 找到正確的實作。 這就是 動態派發（dynamic dispatch）。

所以可以先記住一個很實用的判斷方式：

  • 編譯期就知道具體型別 → 泛型
  • 要等執行時才知道具體型別 → Trait Object

注意：不是「有很多不同型別」就一定要用 trait object。 即使有 PlainFormatter、JsonFormatter 和 XmlFormatter，只要呼叫函式時 Rust 已經知道傳入的是哪一個型別， 仍然可以使用泛型。

真正重要的不是「有幾種型別」，而是： 在這個位置，具體型別現在知不知道？

回到你的 CLI：format 的選擇來自使用者輸入，編譯期無從得知——這正是 trait object 最典型、也最該出場的場景。

你加了一個 --format 旗標，讓工具能用 JSON 格式輸出報告。背後是一個 Formatter trait 加上兩個實作，透過 Box<dyn Formatter> 在執行時選出正確的那一個。
