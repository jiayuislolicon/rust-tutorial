From / Into 與 thiserror

學習目標： 前面的 Lesson 17，你已經看過 impl From， 知道它可以讓 ? 把 io::Error 轉成 AppError。這一課會把這些概念串起來： 先搞懂 From，再理解 Into， 最後使用 thiserror 把錯誤處理的樣板自動化。

1. 先回到我們現在的 AppError

打開 hello_cli/src/errors.rs。 現在的 AppError 大概是這樣： 

#[derive(Debug)]
pub enum AppError {
    ReadFailed(std::io::Error),
    Empty,
    UnknownFlag(String),
    MissingValue(String),
    BadNumber(std::num::ParseIntError),
}

這個 enum 本身沒有問題。問題是：為了讓它真的成為一個好用的錯誤型別， 我們還需要另外寫一些程式碼。

例如，我們需要告訴 Rust：「如果我要把 AppError 印給使用者看，每一種錯誤要顯示什麼？」 

impl fmt::Display for AppError {
    fn fmt(&self, f: &mut fmt::Formatter) -> fmt::Result {
        match self {
            AppError::ReadFailed(e) => write!(f, "讀不到檔案：{}", e),
            AppError::Empty => write!(f, "空檔案"),
            // ...
        }
    }
}

接著，我們還要處理另一件事。假設底層函式回傳：Result<String, std::io::Error>，但我們自己的函式想回傳：Result<String, AppError>，那麼 io::Error 就需要能轉成 AppError。 因此又寫了： 

impl From<std::io::Error> for AppError {
    fn from(e: std::io::Error) -> AppError {
        AppError::ReadFailed(e)
    }
}

ParseIntError 也一樣：

impl From<std::num::ParseIntError> for AppError {
    fn from(e: std::num::ParseIntError) -> AppError {
        AppError::BadNumber(e)
    }
}

於是我們的錯誤型別開始出現一個問題： 每增加一種錯誤，就要到好幾個地方修改。

例如新增一個錯誤，可能就要：

  • 在 enum 裡增加一個變體
  • 在 Display 的 match 裡增加一個分支
  • 再寫一個 From implementation

這些都不是困難的程式碼，但它們非常機械。 而且真正重要的資訊其實很簡單： 

這個錯誤叫什麼
→ 要顯示什麼訊息
→ 要從哪種錯誤轉進來

我們現在卻需要寫很多樣板才能告訴 Rust 這些事情。 所以這一課的目標，就是把這些樣板收起來。

但在使用 thiserror 之前，我們先把其中最重要的一塊搞懂： From。

2. Rust 錯誤處理的核心：From 與 Into 轉換機制

在 Rust 中，處理不同來源的錯誤時，核心關鍵在於型別之間的自動轉換機制。這個機制主要由 From 與 Into 這兩個 Trait 組成。

1. From Trait 的核心概念

From<A> for B 代表「定義如何將型別 A 轉換為型別 B」。

impl From<std::io::Error> for AppError {
    fn from(e: std::io::Error) -> AppError {
        AppError::ReadFailed(e)
    }
}

// 顯式轉換呼叫
let app_error = AppError::from(io_error);
💡 觀念總結： From 負責定義不同型別之間「如何轉換」的具體規則。

2. ? 運算子與 From 的協同作業

當函式宣告回傳 Result<T, AppError>，但內部呼叫的 API 回傳 Result<T, io::Error> 時，? 運算子會在失敗時自動尋找對應的 From 實作並完成轉型：

fn load_report() -> Result<Report, AppError> {
    // 若失敗，io::Error 會透過 From 自動轉為 AppError 並 return Err
    let content = std::fs::read_to_string("report.txt")?;
    // ...
}

轉換流程如下：

read_to_string() 失敗 ➔ Err(io::Error) ➔ 觸發 From 轉型 ➔ 回傳 Err(AppError)

3. Into 與 From 的雙向關係

Into 並非新的轉換邏輯，它只是從「來源型別」視角出發的反向語法糖。以下兩種寫法執行的是完全相同的轉換：

// 1. 以目標型別為主體（From）
AppError::from(io_error);

// 2. 以來源型別為主體（Into）
let app_error: AppError = io_error.into();
💡 Rust 自動對稱規則： 只要實作了 From<A> for B，Rust 就會自動補全 Into<B> for A，開發者切勿重複實作 Into。

4. 如何心智模型化 .into()

在程式碼中看到 value.into() 時，不需視為特殊的語法魔法。請直接理解為：「依據目標型別需求，自動呼叫預先實作好的 From 規則來轉換轉換型別」。Into 只是 From 機制的另一個介面入口。例如：

let error: AppError = io_error.into();

可以在腦中翻譯成：

io_error
   ↓
之前定義好的 From for AppError
   ↓
AppError

這樣 Into 就不會變成另一個需要死記的概念。 它只是 From 的另一個入口。

3. 痛點：手寫 Error 型別有太多的樣板碼（Boilerplate）

標準 Rust 錯誤型別需要實現三種能力：Display（錯誤訊息）、From（轉換外部錯誤）與 Error（標示為標準錯誤）。 

AppError
│
├─ Display  └─ 錯誤要顯示什麼
├─ From     └─ 外部錯誤怎麼轉進來
└─ Error    └─ 宣告這是一個標準的錯誤型別

以前為了將 std::io::Error 轉成 AppError::ReadFailed，我們必須手寫大量的樣板： 

impl From<std::io::Error> for AppError {
    fn from(e: std::io::Error) -> AppError {
        AppError::ReadFailed(e)
    }
}

解決方案：使用 thiserror 庫，直接把這些轉換與顯示規則宣告在 enum 上。

4. 使用 thiserror 重構與屬性解析

安裝並導入 thiserror 後，原本冗長的實作可以濃縮為：

use thiserror::Error;

#[derive(Error, Debug)]
pub enum AppError {
    #[error("讀不到檔案：{0}")]
    ReadFailed(#[from] std::io::Error),

    #[error("空檔案")]
    Empty,

    #[error("數字格式錯誤：{0}")]
    BadNumber(#[from] std::num::ParseIntError),
}

主要由兩個核心屬性取代手寫程式碼：

  • #[error(...)]：取代手寫 Display。格式化字串中的 {0} 對應變體的第一個欄位。
  • #[from]：取代手寫 From。自動生成轉換邏輯，讓 ? 運算子可以直接運作： 
    #[from] → 自動產生 From → 自動得到 Into → 支援 ? 運算子

5. 外部錯誤 vs 自訂錯誤與架構總覽

並非每個錯誤變體都需要 #[from]，理解兩者的區別很重要：

【外部錯誤】
std::io::Error ──( From / #[from] )──> AppError::ReadFailed

【自訂錯誤】
程式判斷「檔案是空的」 ──( 直接建立 )──> AppError::Empty

最後，#[derive(Error, Debug)] 自動整合所有元件，幫我們省去了手寫 std::error::Error 的心智負擔：

#[derive(Error, Debug)]
│
├── Debug
└── Error
      │
      ├── #[error(...)] → 自動產生 Display 訊息
      └── #[from]       → 自動產生 From 轉換

6. 前後對照

🔴 手寫 Display + From
impl fmt::Display for AppError {
    fn fmt(&self, f: &mut fmt::Formatter) -> fmt::Result {
        match self { /* 每個變體一行 write! */ }
    }
}

impl From<std::io::Error> for AppError {
    fn from(e: std::io::Error) -> AppError {
        AppError::ReadFailed(e)
    }
}
// BadNumber 再來一個 From...
🟢 thiserror 屬性
#[derive(Error, Debug)]
pub enum AppError {
    #[error("讀不到檔案：{0}")]
    ReadFailed(#[from] std::io::Error),
    #[error("空檔案")]
    Empty,
    // ...
}

行為不變：load_report 裡的 ? 照舊、eprintln!("{}", error) 照舊、訊息字串也照舊。變的是訊息與轉換規則都寫在變體旁邊，不用再到檔案另一頭找 match。

7. 動手做

  1. 在 hello_cli/ 執行 cargo add thiserror。
  2. 改寫 errors.rs：刪掉手寫的 impl Display 與兩個 impl From，改成上面的 #[derive(Error, Debug)] 版本。記得 use thiserror::Error;。
  3. 跑 cargo test。既有測試加上 errors 模組裡的兩支測試都要通過——尤其是 io_error_converts_via_into。
  4. 再跑一次失敗路徑確認訊息沒變： cargo run -- no-such-file.rs，stderr 應仍以「讀不到檔案：」開頭。
💡 main.rs、report.rs、formatter.rs 都不需要改。錯誤的形狀與訊息沒變，只是產生 Display／From／Error 的方式變了。

錯誤處理這條線到這裡告一段落：你知道轉換從哪來，也知道樣板可以交給 crate。

三件帶走的事：
  • From／Into——同一轉換的兩面；實作 From，免費得到 Into
  • std::error::Error——給錯誤型別一枚完工章；函式庫常在 bound 裡要求它
  • thiserror——用 #[error] 與 #[from] 產生 Display、Error、From
