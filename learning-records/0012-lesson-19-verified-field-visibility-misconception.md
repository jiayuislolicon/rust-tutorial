# 0012 — Lesson 19 exercise verified complete; corrected misconception about field-level `pub`

User completed the Lesson 19 exercise (split `main.rs` into `errors.rs`/`report.rs`/`main.rs`) and hit a real compile error: `main.rs` accessed `report.content` directly and got `E0616: field content of struct Report is private`, despite `struct Report` already being `pub`. This confirmed a genuine misconception — the user assumed marking the struct `pub` made all its fields visible too, and was surprised to learn struct-level and field-level visibility are independent in Rust (fields default to private regardless of the struct's own visibility). GLOSSARY.md's `pub` entry already stated this rule, so the gap was in the user's mental model, not missing material.

User's chosen fix: add `pub` to all three fields individually, rather than the encapsulation-preserving alternative (keep fields private, add accessor methods) that the lesson's exercise steps had modeled. This is a valid but different design choice — worth watching for follow-on effects (e.g. external code now able to mutate `report.content` directly, bypassing `add_title()`).

Verified with `cargo build` (clean, one pre-existing unrelated warning — see below) and all three manual test cases (real file, missing file, empty file) via `cargo run`, matching Lesson 18 output and exit codes exactly.

**Pre-existing warning noticed, not yet addressed**: `report::Report::classify_line` is `pub fn` but returns `LineKind`, which is a private enum — `warning: type LineKind is more private than the item ... classify_line`. This surfaced only now that `report` is a separate module with a `pub` `Report`; it didn't matter when everything lived in one file pre-Lesson-19. `classify_line` isn't actually called from outside `report.rs` (only internally by `count_kinds`), so the fix is likely dropping its `pub`, not making `LineKind` public — a good candidate for a future lesson's "read a warning, decide the minimal fix" exercise.
